# 設計

## 1. 目的と最優先の要件

- 入力: 『全国数学教育学会誌 数学教育学研究』のテンプレート（`tests/fixtures/JASME_template_20261009.docx`）で作成された論文の docx
- 出力: J-STAGE 全文 XML（JATS 1.1 Journal Publishing、FULL-J）と、J-STAGE のアップロード用フォルダ構成の ZIP、変換レポート
- **最優先: docx の本文の文字を 1 文字も変えない**（誤字脱字も直さない）。リンクの誤りは許容されるが、少ないほどよい。
  受け取った docx が出版版と違うときのために、先に docx を出版版 PDF に合わせて直してから変換する作り方も選べる（4.4 のルート2）。
  そのときも、docx → XML の処理は同じで、XML は（直した）docx の文字と 1 文字も違わない。

## 2. 実行環境の選択（Google Colab）

| 案 | 利点 | 欠点 |
|---|---|---|
| **Google Colab のノートブック（採用）** | ブラウザと Google アカウントだけで動く。ノートブックが毎回 GitHub から最新のコードを入れるので、コードの写しが散らばらない。ファイルは利用者自身の一時的な実行環境で処理される | 実行のたびに準備（1〜3 分）が要る |
| Web アプリ（Streamlit 等を常時公開） | 最も簡単に使える | サーバーの維持・費用・管理者が必要。未公開原稿を外部サーバーに上げることになる |
| GitHub Actions で変換 | 記録が自動で残る | 原稿をリポジトリに置く必要がある（公開リポジトリでは不可） |
| 配布用の実行ファイル | オフラインで動く | OS ごとの作成・更新が必要。EMF 変換の LibreOffice を同梱できない |

変換の本体は Python のパッケージ（`src/jasme_jats/`）で、Colab のノートブックはその薄い操作画面にすぎない。
同じパッケージがパソコンのコマンドラインでも、GitHub Actions のテストでも動く。

## 3. 処理の流れ（`pipeline.py`）

1. **読み取り**（`docx_reader.py`）: docx の XML を直接読み、段落を「アトム」（文字・数式・画像・脚注参照・生成文字）の列にする。
2. **構造化**（`structure.py`）: スタイル名から段落の役割を決め、題目・著者・本文（章節項）・図表・注・文献・英文要旨・資料の構造（`ArticlePlan`）を組み立てる。
   スタイルが想定外の段落は、番号の形式などから機械的に推定し、`Decision` として記録する。
3. **機械的リンク**（`linker.py`, `refparse.py`）: 図・表・数式・注・引用文献・URL・DOI。
4. **AI 補完（任意）**（`ai_assist.py`）: AI が返した操作を検証し、構造の組み直しとリンクの追加として適用する。
5. **XML の組み立て**（`builder.py`, `emit.py`）
6. **文字の不変性チェック**（`fidelity.py`）… AI 補完を行った場合も必ずここで行う
7. **最終出力の再チェック**: 目印を取り除いた XML を直列化して読み直し、文字列が検証済みの木と一致することを確かめる
8. **DTD 検証**（`validate.py`）: 同梱の J-STAGE 指定 DTD
9. **画像の出力漏れの検出**（`pipeline.lost_images`）: docx の画像のうち、XML に出力しなかったものを調べる（4.3）
10. **J-STAGE のアップロード時チェック**（`jstage_rules.py`）: 記事アップロードメッセージ一覧のうち、XML だけで判定できるもの（6 章）。
   画像の名前を使うので、実際には 11 の画像の書き出しの後、ZIP を作る前に、出力した画像の名前で行う
11. **画像・ZIP・レポート**（`images.py`, `package.py`, `report.py`）: アップロード用の ZIP には、今回の変換で作った XML、今回指定した PDF、
   `Graphics/` のうち出力できた画像だけを入れる（`package.upload_entries`）。作った ZIP は読み直して、名前の文字・記事フォルダの外の項目・
   想定外のファイル・0 バイトのファイル・XML があることを確かめる（`package.zip_problems`。6 章）

記事の PDF があれば、4 の AI 補完と 5 の組み立ての後、6 の不変性チェックの前に、docx の段落と PDF の文字を照合する（`pdfmatch.py`。4.4）。
ルート2 で Word の番号（自動番号・脚注番号）の全角・半角を PDF に合わせるときは、照合の後で 5 の組み立てをやり直す。
ルート2（出版版 PDF に合わせてから作る）では、1 の前に、PDF に合わせて直した docx を作り（`pdfdocx.py`）、以降はそれを入力にする。

## 4. 文字を変えないしくみ

### 4.1 文字ポリシー（`ooxml.py` の冒頭）

「docx の文字」を次のように定義する。

- 含める: `w:t`、数式中の `m:t`、タブ（`w:tab` → タブ文字）、改行（`w:br`, `w:cr` → 改行文字）、`w:noBreakHyphen`、`w:softHyphen`、`w:sym`（Symbol フォントは Unicode に対応付け）
- 含めない: 削除された変更履歴、フィールドコード、隠し文字、ページ区切り、ルビの読み、テキストボックス内の段落（別の段落として扱う）
- Word が自動生成する文字（自動段落番号・脚注番号）は docx の文字ではない。XML では「生成文字」として区別し、レポートに記録する。
  docx にない注の見出し（Word の脚注機能で書かれた注）を補う場合も、生成文字として区別する（6 章の「注」）。

### 4.2 変換中の目印と照合

- 中間表現は、段落の文字をアトムの列として持つ。リンク付けはアトムに `LinkSpec` を付けるだけで、文字列は変えない。
- XML の組み立てでは、段落の文字を必ず `<jx:span src="段落ID" seq="n">` の中に書く（`tracking.py`）。
- `fidelity.verify()` は、docx から **別の実装**（`ooxml.canonical_text()`）で段落ごとの文字列を取り出し、XML の `jx:span` の文字列と比較する。
  - すべての段落が、XML に出力されているか、出力しない理由（`Exclusion`）が記録されているか
  - 目印の外に文字がないか（docx にない文字の追加の検出）
  - 構造の区切りとして落とした文字（`jx:drop`）が空白だけか
  - 同じ段落を二重に出力していないか
  - 出力した段落が、出力しない段落（`Exclusion`）にも記録されていないか（レポートの「出力しなかった文字」と食い違う）
  - 空白だけの段落として記録した除外（`Exclusion.blank`）の docx の文字が、本当に空白だけか（同じ段落の除外が 2 件以上あっても、すべて確かめる）
  - 上の 2 つに当たるものは、レポートの 5 章に「変換ツールの不具合」として出し、不合格にする
- 照合後に目印を取り除き（タグを外すだけ）、直列化した最終出力を読み直して、文字列が一致することを `final_check()` で確かめる。
- `tests/test_fidelity.py` で、わざと文字を変える・段落を消す・文字を足す・段落を二重にする・出力した段落を除外にも記録する・
  文字のある段落を空白だけとして除外する、などの改変がすべて検出されることを確かめている。

### 4.3 出力しない文字・落とす空白・生成文字

- 出力しない段落（`Exclusion`）: テンプレートの誌名行・装飾行（❚❚❚）、空白だけの段落、重複する所属、図の一部とみなしたテキストボックスの文字など。レポートに全文を載せる。
  空白だけの段落（全角空白だけのものも）は `ArticlePlan.exclude_blank()` で記録する（理由「空白のみの段落」、`blank=True`）。
  図の画像だけの段落にある空白も `blank=True` で記録する。画像と文字が同じ段落を図に組むときは、文字を除外せず、
  画像だけを図に移して、段落は図の直後に本文の段落として出す（`structure.Classifier.float_mechanical`・`float_from_spec`）。
- 落とす空白（`jx:drop`）: 姓と名の間（JATS では `<surname>` と `<given-names>` に分けるため）。`split_labels = true` のときは図表番号・章番号・注番号とタイトルの間も。空白以外は落とさない。
- 数式: OMML では属性で表される括弧などの記号は MathML の `<mo>` になるため、`jx:implicit` を付けて照合から除く。根号の指数のように MathML で順序が入れ替わる文字は、`jx:o`（docx 上の順序）で並べ直して照合する。
- 画像: 不変性チェックは文字しか見ないので、画像は別に確かめる。組み立ての後に、docx の画像（`Document.images`）のうち、XML に出力した画像
  （`BuildInfo.images`）に入らなかったものを `pipeline.lost_images()` が調べ、`Result.lost_images` に記録する。画像を出力できない場所
  （題目・著者名・所属・引用文献・番号。`emit.Ctx` の `images=False`）の段落や、出力しなかった段落（`Exclusion`）の中の画像がこれに当たる。
  理由は、その段落の文字を XML のどこに出力したか（`jx:span` の祖先の要素）と、除外の記録から推定する。変換の結果は変えず、要対応として
  レポートの冒頭・9 章・14 章、Colab の赤い枠、コマンドラインの標準エラー（終了コード 1）に出す（対処は、Word でその画像を本文の段落に
  移して変換し直すこと）。隠し文字のランの中の画像（`ImageRef.hidden`）は、隠し文字と同じく Word で表示されないので出力せず、
  レポートの 6 章・9 章に載せるだけにする。
- 文字だけのテキストボックスの段落と、Word の文末脚注は、今は XML に出力できず、除外としてレポートの 6 章に載る。見落とされないよう、
  除外したときは件数と対処（Word でテキストボックスの外に出す、本文の注に移す）を、レポートの冒頭と 14 章に「要確認」として出す
  （`report.provisional_exclusions`。XML に出力できるようになるまでの暫定の知らせ）。

### 4.4 出版版 PDF との照合と、2 通りの作り方（`pdfmatch.py`, `pdfdocx.py`）

受け取った docx が、著者校正を経た最終版とは限らない（組版で印刷所がかっこ・句読点を全角にそろえる、校正の直しが docx に戻されていない
など）。J-STAGE では PDF と全文 XML の両方が公開されるので、XML の本文が PDF と違えば、同じ記事に 2 つの版が並ぶことになる。
そこで、記事の PDF があるときは docx の段落と PDF の文字を照合する。**PDF から XML を作るのではない**
（構造はすべて docx のスタイルから決める。PDF からではスタイルが使えず、組版の都合の文字も混じる）。

作り方は 2 通りで、最初に利用者が選ぶ（Colab の手順 2 の `ROUTE`、コマンドラインの `--route`、`Options.route`）。
Colab の初期値はルート2（PDF がないときは利用者がルート1 を選ぶ）。コマンドラインは `--pdf` があればルート2、なければルート1 が既定。
`Options.route` の既定は、PDF がなくても動くようにルート1（`"docx"`）。

- **ルート1「docx から作る」**（`route="docx"`）: docx の文字のまま XML にする。PDF があれば照合して、違いをレポートの 13 章に
  載せるだけ（冒頭とチェックリストにも件数を出す）。docx を直して変換し直すか、ルート2 で変換し直すかは人が判断する。
- **ルート2「出版版 PDF に合わせてから作る」**（`route="pdf"`。PDF が必須）: 先に、docx の文字を PDF に合わせて直した docx
  （`巻_開始ページ_PDFに合わせた原稿.docx`。Word の変更履歴つき）を作り、それをルート1 と同じ処理で変換する。直した docx は出力
  フォルダに置く（Colab では手順 8 でダウンロードする「変換結果」の ZIP に入る）。Word で開いて変更を 1 つずつ確かめ、却下したい変更が
  あれば、却下して保存した docx をルート1 で変換し直す。

照合（`pdfmatch.py`。どちらのルートでも同じ）:

- PDF の文字（pypdfium2）から、空白とページ番号を除いた列を作る（`pdf_stream`。次の項目）。docx の全段落（表のセル・図の中の文字も
  含む）を docx の順につないだ列と PDF の列を、まとめて照合する（`_joint`）: どちらにも 1 回だけ出る 8 文字の並び（アンカー）の最
  長増加列で単調に（順序を保って）対応させ、アンカーの間を difflib で埋めて、段落ごとの「塊」（PDF の中で続いて一致した部分）にす
  る。単調な対応に入らなかった段落や段落の一部（2 段組みの読み順のずれ、表の後ろに出た段落の最後の行など）は、隣の塊のすぐ隣、次
  （前）の本文の段落のすぐ前（後ろ）、アンカーの順に探す（どれもない短い段落は、前後の段落の間か、段落の一部の文字列が PDF の中に
  1 回だけ出る位置で探す。前後の段落の間では、行全体でしか一致させない行の文字も、行全体が段落の文字の中にあれば使う。くり返し示す
  問題文など、同じ文字の段落の最初の行が何ページにも出る形）。段落の最後（最初）の部分は、表・図・ほかの段落の後ろ（前）に出て、
  校正で一部が直されていても（表の後ろに出た最後の行「…持った。」と docx の「…取った。」）、docx ですぐ後ろ（前）の本文の段落の
  すぐ前（後ろ）の行まるごとが、その部分の文字の半分以上と一致し、最後（最初）の文字も同じなら、その行に置く（`_loose_edge`。間に
  ある照合に使わない行だけの行〈1 ページ目の最後の投稿受付日の行、次のページの最初の柱など〉は 3 行まで飛ばす）。ただし、その
  部分が docx で一文まるごと（段落の最後なら文の終わりの直後から始まり、段落の最初なら文の終わりか読点で終わる。校正で消された
  文や、書き出しの「そこで，」かもしれない）のときは、似た行（すぐ後ろの図の中の「問題を解きなさい。」と、消された「その問題を
  示す。」）に一致した文字だけで置くことはしない（置くと、図の中の文字で docx の文字を置き換えてしまう）。段落の最後（最初）の
  docx の文字がどの塊にも入らないときは、段落の最後（最初）の行の 1〜2 文字の一致も、偶然の一致として外して探し直す（段落の
  最後の数文字が小さな図の後ろに出たとき、図の中の行「前時の表を振り返る」のよく使う文字「時」「を」が、段落の最後の
  「時間を取った。」と並べられ、図の中の文字「の表」で docx の文字を置き換えないように）。
  段落ごとに照合する PDF の窓（`_window_lines`。列の位置のリスト）は、
  段落の塊のある行と、そのすぐ前後の照合に使わない行（柱の候補の行など）で作り、ほかの段落の塊の文字は入れない。2 つの段落の塊が同
  じ行にあるときは、行の始まり・終わりを段落の境目にしやすくして境目を決め直す（`_contests`。校正で消された段落の最後の文字が、次
  の段落の書き出しと並べられないように。行の境目の点は、1 文字の一致より小さくする〈次の段落の書き出しの 1 文字を前の段落のものに
  しないように〉）。境目の候補が同じ点で 2 つ以上あるとき（間の文字が、校正で直された・足された、どちらの段落の docx の文字とも
  一致しない文字のとき。docx では 2 つの段落が、PDF では 1 つにつながったものや、追い込みの見出し）は、文の終わりの直後、同じ行の
  中の全角の空白の直前（追い込みの見出しと本文の間）の順に決める（「確かめる」→「確かめた。」の「た。」を、次の段落の頭に
  足さない）。決められなければ、どちらの段落の最初・最後の違いも直さない（`EDGE_WHY`。間の文字は両方の段落の 13 章に出す）。
  前の段落の最後の直し（「確かめる」→「確かめて」）と、前の段落の最後の削除と次の段落の書き出しの挿入（「る」を消して
  「そこで」を足す）は PDF から区別できないので、docx の直された文字がどちらの段落にあるかでは決めない（決めると、片方の形で、
  次の段落に足された語を前の段落に足し〈「…確かめそこで」〉、次の段落の語を落とす）。
  段落ごとの照合（`_align`）では、全角・半角、大文字・小文字、ハイフン・ダッシュの違いは無視して位置を合わせ、段落の途中の、PDF の 1 行の中だけの 1〜2 文字の一致（docx にない表のキャプションの「表１」の「１」と docx の
  「12点」の「1」など。`_line_islands`）と、投稿受付日の文字列の一部だけとの一致（`_date_islands`）は、偶然の一致として外して照合
  し直す。一致した文字が 85% 未満の段落は「PDF に見つからない段落」とする。数式・画像は照合しない。段落の最初・最後の違いは、PDF
  の同じ行の文字だけを使う（前の行の見出しなどを段落の文字と取り違えないため）。0.20.0 までは、全体の照合で決めた段落ごとの窓（段
  落の長さ + 60 文字ほど）と照合していたので、PDF の中で段落が長い表・図の中の文字・ほかの段落で分断されると、段落の後ろ（前）が窓
  の外に出て窓の中のほかの文字と並べられ、ルート2 で docx の本文を消したり、別の文字に置き換えたり、図の中の文字を足したりしていた
  （0.21.0 で、分断された部分も段落の文字として照合し、そこにある校正の直しも直すようにした。照合の時間も、本誌の出版版 PDF で
  0.20.0 の 10 分の 1 ほどになった）。
- 組版で入る文字（ページ番号・誌名の行・柱・投稿受付日など）は docx にない。docx では画像・Word の表になっている図・表の中の
  文字（図の中の点の名前、表のセルの数字など）も、PDF では本文の行と同じに取り出される。段落の途中にあると PDF にだけある文字として
  違いになり、ルート2 では docx に足されてしまうので、ページの区切りの位置と文字の形で見分けて、照合に使わない（`pdf_stream`・
  `PdfStream.ignored`）。
  - ページ番号: 各ページの空でない最初の行と最後の行のうち、数字だけの行（「（25）」「－ 1 －」など。`RE_PAGE_NO`）で、ページの順に
    番号が続いているもの（数とページの順番の差が、ほかのページと同じもの）を列から除く（1 ページに 1 つ。`_page_numbers`。本誌の
    出版版 PDF では、すべてのページの最初の行の「（25）」）。ページ番号がページの最後にある PDF で、ページの最初の行が引用文献の
    「pp.11-」の続きの「16」でも、「16」は除かない。番号が続く候補がどのページにもない（1 ページだけ、ページ番号のない PDF など）
    ときは、最初の行、それがなければ最後の行の候補を除く。ただし、前の行の続きの数字（下の「行全体でしか一致させない行」の項。
    ページの最後の行が「pp.11-」の改行の後の「16」のときなど）は除かない。ページの途中の数字だけの行は除かない（引用文献の
    「pp.11-」の改行の後の「16」や、表のセルのことがある。除くと、ルート2 で docx のその数字を消してしまう）。

  として無視するので、docx のダッシュを消してしまう）、PDF の英数字の後の行末の「-」と並べば、PDF に合わせて「-」に直す（行の途中の
  ダッシュと「-」と同じ。修正計画の決定事項 20・23。0.20.0 は docx のダッシュを消していた）。PDF の行末が U+FFFE なら、どれも
  docx のまま（違いにしない）。
- 照合する段落: 題目・見出し・本文・キャプション・注・付記・謝辞・引用文献・英文要旨（表のセル・別行の数式・資料、4 文字未満の段落は除く）。
  図形の中の表のセルの画像とキャプションで組んだ図（6.1。`cell_figures`）のキャプションと、画像と同じ段落の文字も、docx では表の
  セルなので除く（0.21.0 と同じ。`linker.body_paragraphs` の文脈 cell）。
- 違いは次の 3 種類に分ける（`PdfCheck`）。
  - **英数字・記号の全角・半角だけの違い**（U+0021〜U+007E と U+FF01〜U+FF5E。`width`）と、その文字のすぐ前後の docx の空白で
    PDF にないもの（`drops`。「理論 (ATD) に」→「理論（ATD）に」）。PDF の空白は両端そろえや字間でも見えるので、前後がどちらも
    ラテン文字（英文の単語の間）のときだけ本物の空白とみなす。URL・DOI などのリンクの文字は対象にしない。
  - **それ以外の違い**（`diffs`。「資料」と「付録」、引用符の ' と ’、大文字・小文字、「〜」と「～」など）。図の中の文字と思われる
    PDF の文字（ほかの段落に当たった文字、20 文字以上続く PDF にだけある文字）は除く。20 文字の長さは、照合に使わない文字を除く
    前の文字で数え（図の中の文字の行がページの端にかかって除かれても、残りを足さないように）、行全体でしか一致させない行の文字は
    数えない（0.19.0 と同じ長さ。表の数字の行や柱のすぐ隣の、校正で足された短い文字まで足さないことにならないように）。
    20 文字以上の文字が段落の文字のある行にかかるときは、校正で足された本文かもしれないので、黙って捨てずに直さない違い
    （`fixable=False`。理由は `LONG_WHY`）として 13 章に出す。かからないとき（図の中の文字の行など）は、その行を照合に使わなかった
    文字の一覧に載せる。
    数式・Word が付ける番号・リンクの文字にかかるもの、足す位置を決められないもの、PDF の側に組版で入る文字しかないもの、
    上の項目で決められないとしたものは `fixable=False`（ルート2 でも直さない）。
  - **Word が付ける番号**（自動段落番号、Word の脚注機能の脚注番号。`numbers`）: docx の文字ではなくツールが作って出力する文字。
    照合では出力する文字（自動番号は Word の表示、脚注番号は設定 `fn_mark`）を段落の文字列に入れて PDF と比べる。

PDF に合わせて直した docx（`pdfdocx.py`。ルート2）:

- 照合の結果から直す箇所（`Fix`）を決める: 全角・半角、その前後の PDF にない空白、それ以外の違い（文字ごとに最小限の変更にし、
  docx の空白は消さない。空白だけの違いは直さない）。表のセル・数式・図の中の文字、PDF に見つからない段落は直さない。
  組版で入る文字（ページ番号・誌名の行・柱・投稿受付日など）とみなして照合に使わなかった文字は、docx に足さない。重なる直す
  箇所は後のものを直さず、1 つの違いを文字ごとに分けた直す箇所の一部がほかの直す箇所と重なるときは、その違いの直す箇所を
  すべて直さない（一部だけを当てはめると、docx にも PDF にもない文字になる）。
- 元の docx の XML（前処理しないもの）のランを分けて、削除（`w:del`）と挿入（`w:ins`）の変更履歴として書き込む。書式（太字・
  上付きなど）は直す文字のランのものをそのまま使い、スタイル・数式・図・注はそのまま。直せるのは `w:t` の文字と、Word の改行
  なしハイフン（`w:noBreakHyphen`。読み取りでは「‑」。要素ごと削除の変更履歴にして、PDF の「-」を挿入する。ダッシュ・ハイフンの
  仲間を PDF に合わせるため）だけで、タブ・記号・フィールドの結果・既存の変更履歴やハイパーリンクの中の文字にかかるもの、段落の
  文字列を読み取りと同じに組み立てられない段落（図形を含む段落など）は直さない。本ツールの読み取りは、挿入を残し削除を除いた
  文字（すべて承諾した状態）を読む。
- 書き込んだ後に読み直して確かめ、合わない箇所は直さずに作り直す: (1) 直した段落の文字列が直した結果と一致するか、
  (2) 段落の役割・リンク（注・引用文献・図表など）・注の区切りが元の docx と同じに決まるか。(2) で崩れたリンクは、リンクの文字に
  かかる変更 → リンク先の段落（引用文献・注。PDF に合わせて著者名が変わり、本文の引用と照合できなくなった場合など）→ リンクのある
  段落全体、の順に直さないことにして作り直し、守る範囲を広げても直らなければ何も直さない。注の番号は、1 つでも直せないときは
  すべての注で docx のままにする（本文の「（注1）」が PDF では上付きの「1）」のときなど。書式までは直さないので、直すと注を認識
  できなくなる）。
- Word が付ける番号は、変換のときに全角・半角だけの違いなら PDF に合わせて出力する（`PdfCheck.number_edits` → `plan.pdf_numbers`。
  本文の脚注番号「1)」→「1）」、注の一覧「1)」→「１）」など）。番号が全角の文字で終わるときは、番号の後に空白を補わない。
- レポートの 13 章に、直した箇所（段落ごとに変更前→変更後）、直さなかった箇所と理由、Word の番号、直した docx をもう一度 PDF と
  照合して残っている違い、PDF に見つからない段落、照合に使わなかった PDF の文字（組版で入る文字とみなしたもの。元の docx との
  照合のもの）を載せる。不変性チェックの相手は直した docx。

## 5. AI 補完の設計

- AI には XML も docx も直接編集させない。AI が返すのは操作の一覧（JSON。`ai_assist.RESPONSE_SCHEMA`）だけ。
- 操作の種類: `link_citation`（年の部分のみ）/ `link_figure` / `link_table` / `link_note` / `link_formula` / `set_role` / `formula_image` / `split_name`
- プログラムによる検証（`apply_ops`）:
  - 対象の段落・文字列（完全一致）・リンク先が存在するか
  - 引用文献へのリンクの文字列が「年」か（利用者の指定した規則を機械的に強制する）
  - 数式・画像をまたがないか、既存のリンクと重ならないか
  - 役割の指定がその位置で可能か（注の一覧の段落では、`fn_start`（新しい注の始まり）と `p`（前の注の続き）で注の区切りを指定できる。
    Word の脚注機能で書かれた注は Word の区切りのとおりで、変えられない）
  - MathML が MathML の要素だけでできているか（それ以外の要素は不採用、未知の属性は除去）
  - 姓 + 名 が氏名の文字列と一致するか
- 位置を機械的に決められなかった浮動配置の図表（6.1）は、`operations` とは別の `placements` で、図形ごとに置く位置（`after`: その直後に置く段落）と
  中身の組み合わせ（`items`: 図・表ごとのキャプションの段落と本体）を必ず指定させる。回答の JSON は `placements` を最初に書かせる
  （`RESPONSE_SCHEMA` の順、`SYSTEM_PROMPT`、手動モードの依頼文の見本・項目の説明・回答の書き方。回答が長すぎて途中で切れても、
  位置の指定が残るように）。検証（`float_placements`）:
  - 図形が「位置を決められなかった図表」にあるか（機械的に配置した図形は変更させない。依頼文でも「変更不可」として示す）
  - `after` が本文の段落か（図形の中の段落・表のセル・本文以外は不可）。本文の外（注・引用文献・付記・謝辞・英文の部分・資料。
    `structure.AFTER_BODY_REGIONS`）の段落を指定したものも採用しないが、その図表は本文の冒頭ではなく本文の最後に仮に置く
    （決定事項 21。不採用の理由にもそう書く。同じ図形に後ろで正しい指定があれば、そちらを採用する）
  - キャプション・本体が、その図形の中の段落・表・画像か。本体の段落に画像があるか（文字だけの段落を図の本体にすると落ちるため。
    画像と文字が同じ段落は本体にでき、画像を図に入れ、段落は文字ごと図の直後に本文の段落として出す。6.1）
  - 同じ中身を 2 回使っていないか、表を「表全体」と「セルの段落」の両方で使っていないか
  - 指定に含まれなかった中身は、図表の後にそのまま出す（文字を落とさない）
- 図形の中の段落への `set_role` は不採用にする（`placements` で指定させる）。
- `set_role` または `placements` を含む場合は、docx を読み直して構造を最初から組み立て直してから、他の操作を適用する。
  組み直すと図表の並びが変わって ID（F1 など）がずれることがあるため、AI が依頼文の ID で指定したリンク先は、キャプションなどの段落 ID を目印にして組み直した後の ID に読み替えてから適用する（`target_keys` / `retarget_ops`）。
  `fn_start` で新しく分けた注は依頼文に ID がないため、`link_note` のリンク先はその注の最初の段落の ID で指定させ、組み直した後の注の ID に読み替える。
- 位置を決められない図表は、AI に渡す前の組み立てではアンカー段落のすぐ後ろに仮に置くが（6.1）、依頼文の段落一覧は docx の順で、位置の手がかり（アンカー段落・距離・行数の推定）も docx の記録から作るため、仮の位置は AI の判断に影響しない（依頼文の図表の ID と、推定の「指定がなければ…に仮に置く」は仮の位置で決まる。リンク先は組み直した後の ID に読み替える）。
- 回答の JSON の前後の文字（前置きの説明や、閉じの ``` のないコードブロックの後ろの説明など）は使わず、最初の `{` から最後の `}`
  までを読む（`parse_response`。後ろの文字に `}` があるとき〈JSON が 2 つ続くときなど〉は読めない回答とする）。コードブロックは、
  ```（json）のすぐ後ろが `{` のものだけを使い、閉じの ``` は行の頭にあるものだけとみなす（`_json_text`・`RE_FENCE`。JSON の文字列の
  中の ``` は改行を含められないので行の頭に来ない）。回答が `{` で始まるとき（コードブロックの中身だけをコピーしたときなど）は、
  コードブロックを探さずに回答全体を読む。
- 途中で切れた回答（API の出力の上限、チャットの回答の途中までの貼り付け）は、JSON の読み取りの誤りが回答の最後で切れた形
  （文字列の途中で終わった「Unterminated string」、または「Expecting …」の後ろが空か値の書きかけ。`cut_at_end`）のときだけ、
  最後まで書かれた `placements` の要素を読む（`parse_cut_response`。最上位のキーと値、`placements` の要素を 1 つずつ JSON として
  読み、途中で切れた要素とその後ろは読まない。閉じ括弧を補ったり推測で直したりはしない。`operations` と `notes` は、最後まで
  書かれた要素があっても使わない）。読めた指定も、ふつうの回答と同じく検証する。反映したときは、読み取りの誤りにはせず、
  要対応（AI に出し直してもらう）としてレポートの冒頭・2 章・14 章、Colab の枠、コマンドラインに出す（`AIOutcome.partial`）。
  `placements` に届く前に切れた回答と、途中の書き損じ（飾りの引用符など）の回答は、今までどおり読めない回答として扱う
  （読み取りの誤りには、回答の最後で切れた形なら「途中で切れている可能性」〈最初から出し直してもらい、続きだけを貼り付けない
  よう案内する〉、飾りの引用符なら出し直しの頼み方の案内を付ける）。最後まで書かれた回答の書き損じは、途中で切れた回答として
  読まない: 最後の文字列の閉じだけが飾りの引用符の回答（「Unterminated string」になるが、切れた文字列の中に、すぐ後ろが
  「,」「]」「}」「:」の飾りの引用符がある。`cut_at_end`。文字列の中の「“主張”について」のような飾りの引用符は JSON の文字として
  正しいので、切れた形とみなす）と、閉じの ``` まで書かれたコードブロックの中で JSON が途中で終わっている回答。
- 数式画像は、元の画像を残したまま AI が読み取った MathML を `<alternatives>` で併記する。これは docx の文字ではないため `<jx:ai>` で囲み、
  不変性チェックでは「追加」と扱わず、レポートに別枠で一覧を出す。DTD に合わない場合は自動で取り消す。
- API モードと手動モードは、依頼文の作り方と回答の受け取り方が違うだけで、検証・適用・最終チェックは同じ。
- API の呼び出し（Claude）: 既定モデル `claude-opus-5-5`、構造化出力（JSON スキーマ）、`effort: high`、ストリーミング、拒否時のサーバー側フォールバック（`fallbacks: "default"`）。
- モデル: 既定は動作確認済みの `claude-opus-5-5`（提供終了は 2027-09-22 以降の予定）。指定したモデルが見つからない（提供終了など）ときは、Models API の一覧から最新の Opus を選んで 1 回だけやり直し、レポートに記録する。`auto`（Colab の「自動（最新の Opus）」）では、はじめから最新の Opus を使う。
- API モードの入口は `ai_assist.call_provider()`。Claude（推奨・`call_api()`）のほか、ChatGPT（`call_openai()`。OpenAI の Responses API）、
  Gemini（`call_gemini()`。Google の Gemini API）、Sakana AI（`call_sakana()`。Sakana Namazu・Fugu の OpenAI 互換 Chat Completions API、
  接続先 `https://api.sakana.ai/v1`）に対応する。どれも依頼文と画像を渡して JSON の文字列（`AIOutcome.raw`）を受け取るだけで、
  検証・適用・最終チェックは共通。回答は同じ JSON スキーマ（`RESPONSE_SCHEMA`）で受け取る（OpenAI は strict の json_schema、
  Gemini は `response_json_schema`、Sakana AI は `response_format` の json_schema。Sakana AI では受け付けられなければ指定なしで
  1 回だけやり直し、依頼文に入れた回答の形式（見本と項目の説明）で JSON を返させる）。回答が出力の上限で切れたときは、どの AI でも
  切れたところまでの回答を残し（`AIOutcome.raw`・`cut`）、最後まで書かれた `placements` だけを読む（上限で止まっても JSON が
  最後まで書かれていれば、ふつうに読む）。
- OpenAI 互換の接続先（Sakana AI）には、API キーを必ず明示して渡す（環境変数 `OPENAI_API_KEY` の OpenAI のキーを別の会社に送らないため）。
- Sakana AI は既定で送信内容を学習に使う設定なので、ノートブックで選んだときに、学習への利用を止める（オプトアウトする）よう赤い枠で注意する。
- Claude 以外では、モデルを利用者が指定する（既定値を持たない。モデルの入れ替わりが速く、動作確認もしていないため）。
  Claude Opus と同等以上の性能のモデルを推奨する。API キーの作り方などは利用者が各社の案内で調べる（ノートブックでは説明しない）。
- 推奨を Claude とする理由: 依頼文（`SYSTEM_PROMPT`）と回答の検証を Claude で試して調整しているため。他社のモデルでも、誤った提案は
  検証で捨てられるので本文の文字は変わらないが、補完の効果は下がりうる。

## 6. J-STAGE に合わせた主な判断

| 項目 | 判断 | 理由 |
|---|---|---|

## 6.1 浮動配置の図表（テキストボックス・グループ図形）

2 段組をまたぐ図などは、テキストボックスやグループ図形に図の本体（画像・表）とキャプションを入れて配置されることが多い（2026-10 の実際の論文 3 本すべて）。
docx には Word で表示したときの位置が記録されておらず、記録されているのは図形が結び付いている段落（アンカー段落）と、そこからの距離などだけである。

- 図を置く位置の規則: Word で表示したときに、図の左上の直上にある本文の文章を含む段落の直後（図の直上が別の図表なら、さらにその上の本文）。
- 読み取り（`docx_reader`）: 浮動配置の図形を `Float`（位置の基準・距離・大きさ・折り返し）として記録し、中身の段落・表・画像に `float_id` を付ける。
  段組みと行の設定（`Layout`: 1 段の幅、行送り、1 行の字数）も `w:sectPr` と `w:docGrid` から読む。
- 機械的に配置するのは、図の左上がアンカー段落の左上にあり（縦はアンカー段落の上端から 1 行未満、横はその段の左端から 1 cm 未満。`floats.at_anchor`）、
  中身が単純（キャプション 1 つと本体 1 つ）な場合だけ。このとき、図の左上の直上の本文はアンカー段落の直前の段落なので、図をアンカー段落の前に置く。
- それ以外は「位置を決められない図表」とし、AI に位置と組み合わせを指定させる（5 章の `placements`）。依頼文には、記録された位置の説明と、
  アンカー段落から行数を数えた推定（`floats.estimate_top_left`。ページ・段の区切りは考慮しない目安）を付ける。
- AI による補完を「使わない」設定で位置を決められない図表があれば、変換を中止する（`pipeline.AIRequiredError`。コマンドラインは終了コード 2、
  Colab は手順 5 で赤い枠）。AI の回答を反映した後も残った場合（AI が位置を答えなかった、検証で採用しなかった、回答が途中で切れて
  読めなかった）は、図が結び付いている段落（アンカー段落）のすぐ後ろに仮に置く（決定事項 21。`Classifier.provisional_target`）。
  アンカー段落が、続いた箇条書きの項目（同じ番号の定義）か引用の段落の途中にあるときは、その箇条書き・引用の最後の段落の後ろに
  ずらす（`Classifier.run_end`。アンカー段落のすぐ後ろに置くと箇条書き・引用が 2 つに分かれ、図表を手作業で移しても分かれたまま
  残るため。空のアンカー段落が箇条書きの項目の間にあるときも同じ。AI が指定した位置はずらさない）。箇条書きの項目かどうかは、
  組み立て（`assemble_floats`）と同じに見る（`Classifier.list_or_quote`。画像と文字が同じ段落の項目は項目として数え、画像だけ・
  別行数式だけの項目〈図・数式になる〉、見出しと推定する段落、浮動配置でないテキストボックスの段落の前で止める。間の浮動配置の図形の中身と空白だけの段落は飛ばす）。
  AI が本文の外（注・引用文献など）の段落の後ろを指定した図表は、本文の最後（最後の章の終わり。後付けの前）に仮に置く。
  同じ位置に置く図表は、キャプションの番号順（番号がなければ後ろ、同じ番号なら docx の順）。
  手作業で正しい位置に移すよう、レポートの冒頭（要対応）・3 章（図表ごとに仮に置いた位置。`ArticlePlan.float_place`: 段落「…」の後ろ、
  または本文の最後。仮に置いた位置のすぐ前の段落に文字がなければ、その前の文字のある段落で示す。3 章の場所の欄も、アンカー段落が
  空の段落なら、その前の段落の場所）・14 章のチェックリストと Colab の赤い枠に出す（コマンドラインは終了コード 1）。レポートの冒頭・
  3 章、Colab の枠とコマンドラインは、図表ごとにキャプションと、手作業で移す XML の要素（`structure.float_targets`: 図表の ID
  〈`structure.float_ids`〉と、図形の中身から本文の段落として出した段落。どちらかがあれば、ID のないキャプションのない図も数える。
  どれもなければ「図表の中身」）を示す。中身が単純なら図の本体とキャプションを組にしてから置き、そうでなければ中身をそのまま置く。
  手動モードで AI の回答を貼り戻す前の出力でも、同じ位置に仮に置く。これらは、本文にアンカーのある図形だけの扱いで、本文の外の
  段落に結び付いた図形の中身は、今は、その領域の段落として扱う（7 章）。決定事項 21 の後半（アンカー段落が本文の段落でない図表は
  本文の最後に仮に置く）は、修正計画の F（N7）で本文の外に結び付いた図形を位置を決められない図表にするときに効く（B3 では、
  仮に置く位置の規則 `provisional_target` だけを用意した）。
- 表で組んだ図（問題文など）は `<fig>` の中に `<table-wrap>` を入れる（JATS 1.1 の fig は table-wrap を含められる。修正計画の決定事項 22。
  J-STAGE の画面での表示は要確認）。
- 図形の中の表 1 つのセルに画像と図キャプションが並ぶもの（セルごとに画像とキャプション、画像の行とキャプションの行、キャプション
  1 つで画像がいくつかのもの）は、組み方が一つに決まれば、AI を使わない設定でも、セルの画像を図の本体、セルのキャプションを図の
  キャプションにした図に組む（表としては出さない。`Classifier.cell_figures`。画像だけのセルとキャプションだけのセルが並ぶ表は、
  同じ列の上下か同じ行の左右に隣り合う組が、表全体で一つの向きに決まるときだけ。`cell_pairs`）。セルに表キャプション・キャプションで
  ない文字（「（a）」などの小見出しも）・入れ子の表があるとき、画像とキャプションの組を一つに決められないときは、組まずに、今までどおり
  （0.21.0 と同じ）キャプションのない表として出す（図の左上がアンカー段落の左上にある図形は、AI を使わない設定でも止めず、アンカー
  段落の前に置く。位置を決められない図形は、今までどおり AI に位置と組み合わせを任せる）。セルに画像がない表（図キャプションと
  問題文だけの表など）と、セルに図キャプションがない表も、今までどおり表として出す。組んだ図のキャプションと、画像と同じ段落の文字は、
  docx では表のセルの段落なので、出版版 PDF との照合（4.4）では今までどおり表のセルとして扱う（照合しない・ルート2 で直さない。
  `ArticlePlan.cell_paras`、`linker.body_paragraphs` の文脈 cell）。
- 画像のない図キャプションの直前（図キャプションを図の上に置く原稿では直後）にある、キャプションのない表は、その図の本体にする
  （fig の中の table-wrap。`Classifier.table_for_figure`。どちらの向きかは、画像の図のキャプションが画像の上と下のどちらに多いかで
  決め、画像の図がなければ下とみなす）。表とキャプションの間にほかの段落がある、表に表キャプションが付いている、表が逆の向きにある、
  直後の表の次に表キャプションがある（どちらの表か決められない）ときは組まず、要対応（「図の本体」）としてレポートの冒頭・3 章・
  14 章、Colab の赤い枠、コマンドラインに出す（表の文字は XML に入っているので、終了コードは変えない）。近くにキャプションのない表が
  なければ、今までどおり判断の一覧（4 章）に記録するだけにする。理由ごとの対処（3 章。`report.figure_body_detail`）: 間に段落が
  ある・逆の向きにあるときは、表を図キャプションの隣に置き直す。表に表キャプションが付いているときは、表を動かすのではなく、図の
  本体の画像があるか、表キャプションと図キャプションのどちらが正しいかを確かめる。
- 位置を決められない図表（仮の位置に置いた図形）の中身は、本当はそこにないので、図表を組み立てるとき（`Classifier.assemble_floats`）に、
  その外の要素と組にしない（図キャプションと画像、表キャプションと表、キャプションのない表に後ろの表キャプションを付けること、
  キャプションの続き、本文スタイルの図表キャプションの推定の隣、図の本体の表〈`table_for_figure`〉）。前後の要素は、同じ置き場所の
  要素（図形の外の要素なら図形の外の要素、仮に置いた図形の中身なら、同じ位置に仮に置いた図形の中身）だけで数える

  仮に置くので 1 つの図に組む〈0.21.0 と同じ。Word の原稿で、画像とキャプションを別々の図形にして浮かせる形〉。別々の段落に

  終わりに置く〉と、AI がどちらも本文の外の段落の後ろと答えた図形〈どちらも本文の最後に置く〉は、同じ位置に仮に置くので組にする。

  キャプションと、隣の本文の画像など）。
- 図形の中で画像と文字（説明文など）が同じ段落にあるときは、画像を図の `<graphic>` に入れ（段落の中には出さない）、段落は文字ごと
  図の直後に本文の段落として出す（機械的に組む場合も、AI がその画像や段落を図の本体に指定した場合も同じ。レポートの判断の一覧に記録する）。
  位置を決められない図形なら、手作業で移す XML の要素の知らせに、図表の ID と並べてその段落も示す（「F1・F2 と段落「説明文：…」」。
  図表だけを移すと、段落が仮の位置に残るため）。
  キャプションのない図形では図にしないので、これまでどおり画像も文字も 1 つの段落に出す。
- 図の位置の推定に、記事の PDF は使わない（PDF が docx と同じ版とは限らないため）。
- 領域（和文の冒頭・本文・後付け・英文の部分。`structure.Classifier.split_regions`）は、図形の外の段落・表だけで決める。図形の中の段落・表
  （浮動配置でない VML・行内のテキストボックスの中のものも）では、スタイルや文字にかかわらず領域を切り替えず（図形の中のセクション区切りでも
  切り替えない）、その時点の領域に入れる（テキストボックスの中の「英文要旨」スタイルの段落や「注」だけの段落で、以降の本文と引用文献が
  英文要旨や注に入らないように）。図形の中身は結び付いている段落（アンカー段落）の後ろに並ぶので、アンカー段落と同じ領域に入る。
  ただし、アンカー段落が和文の冒頭の最後の段落（セクション区切り）なら、区切りで切り替えた後の本文に入る（テンプレートの冒頭に図形はない
  ので、本文の中身とみなす。0.18.1 と同じ）。図形の中の題目の段落も、冒頭の最後のセクション区切りで本文に切り替える条件（題目を見たこと）に数える。

## 7. 既知の限界

- Word の図形・グループ図形・グラフは画像化できない（docx に画像ファイルがない。PDF などから画像を用意する）。用意する画像のファイル名と図の題目を、レポートの冒頭（要対応）・14 章のチェックリスト・Colab の赤い枠・コマンドラインの表示に出す（`report.images_to_prepare`）。
  そのときだけ、利用者に画像を求める（Colab の手順 7、コマンドラインの `--images`）。受け取った画像（PNG・JPEG など、または 1 ページの PDF）は
  出力ファイル名の形式にして Graphics/ に入れ、ZIP とレポートを作り直す（`pipeline.add_images`。レポートの 9 章では「利用者が用意」）。
  Word の図形を LibreOffice で描かせて画像を作る方法もあるが、描き方が Word と少し違い、仕上がりを人が確認する必要があるので採らない。
- アップロード用の ZIP には、記事フォルダに残っている前の変換の残り（今回指定しなかった PDF、今回は出力しなかった画像など）を入れないが、
  記事フォルダからは消さない（レポートの 10 章に出す）。Colab の手順 8 でダウンロードする「変換結果」の ZIP（出力フォルダ全体）には残る。
  ZIP の読み直し（`package.zip_problems`）は、名前の文字・記事フォルダの外と中の想定外の項目・0 バイトのファイル・XML があることだけを見る。PDF がない
  こと（EMSGM057E）は 14 章のチェックリストで知らせ、PDF の中身（別の記事の PDF でないかなど）はここでは確かめない。
- 最後のページ（`lpage`）は NFKC で正規化するだけで、文字は確かめない（ZIP 名・フォルダ名に使わないため。「12頁」のような入力も
  知らせずにそのまま XML の `lpage` に入る）。確かめるなら、止めずに知らせる形にする。
- ルビは親文字のみ。
- 引用の抽出は著者・年方式と `[1]` 形式の番号方式。上付き番号の引用方式には未対応（AI 補完で補える）。
- 段落の役割の推定は、番号の形式（「１．」「(1)」「①」）、隣接する画像・表、テキストボックス内の「図N」「表N」からの規則による。
  テンプレートにあるスタイルが別の役割の段落に付いている場合（本文に章見出しスタイルなど）は、スタイルを信じて推定しない。
- テキストボックスやグループ図形に入った図表の位置は、多くの場合 AI の判断になる（6.1）。docx から行数を数えた推定は、ページや段の区切りを考慮しない。
  AI でも決まらなかった図表の仮の位置（アンカー段落の後ろ）は近い位置にすぎず、2 段組では別の段・別のページの図が多いので、手で移す
  作業は残る。仮に置いた図形の中身はその外の要素と組にしないので（6.1。同じ位置に仮に置いた図形の中身どうしは組にする）、
  本文の画像に重ねたキャプションだけの図形を仮に置くと、本文の画像とは組にならない（キャプションだけの図と、キャプションのない
  図になる。AI が位置を指定すれば、今までどおり隣の画像と組にする）。AI の指定で、画像の段落と図キャプションの間や、箇条書き・
  引用の途中の段落の後ろに図表を置いたときは、今までどおり画像とキャプションが組にならない・箇条書き・引用が 2 つに分かれる
  （指定どおりに置く）。仮の位置を箇条書きの終わりにずらすとき、途中の図形の中の段落（浮動配置でないテキストボックスの段落など）の
  前で止めるので、その後ろに同じ箇条書きの項目が続くと、箇条書きが 2 つに分かれる。同じ箇条書き・引用の別々の項目に結び付いた図形と、
  AI がどちらも本文の外の段落の後ろと答えた図形は、同じ位置に仮に置くので組にする（6.1）。仮に置いた図形の中身に引用スタイルや自動番号の
  段落（画像のある段落）があると、隣の本文の `disp-quote`・`list` とまとめられる（箇条書き・引用のまとめは置き場所を見ない。知らせには
  その段落が本文の引用・箇条書きの中にあることは書かない）。手作業で移す知らせ（`structure.float_targets`）は、文字のない段落を
  「段落「」」と示し、キャプションのない画像だけのグループ図形（仮の位置に何も置かず、画像はアンカー段落の中に残る）にも
  「図表の中身を移すこと」と書く。
- AI が回答を `placements` から書くかは AI 次第で、先頭に書かずに途中で切れた回答からは何も反映しない。途中で切れた回答から反映
  するのは位置の指定だけで、リンクなどは出し直しが要る。切れた文字列の中に、文字列を閉じているように見える飾りの引用符（すぐ後ろが
  「,」「]」など）があると、書き損じの回答とみなして何も読まない（0.21.0 と同じく読めない回答として扱う）。
- 画像のない図キャプションの隣に、たまたま別のキャプションのない表があると、その表を図の本体にする（画像が別の理由で見つからない
  図）。判断の一覧（4 章）に記録し、表の文字は失われない。図キャプションを図の上に置く原稿でも、画像の図がなければ下とみなす。
  本文の表（図形でない表）のセルに画像と図キャプションが並ぶものは、今までどおりキャプションのない表として出す。図形の表のセルで
  組んだ図のキャプションは、ルート2 でも PDF に合わせて直さない（0.21.0 と同じく表のセルとして扱う。PDF との違いは 13 章にも
  出ない。AI が組み合わせを指定したときは、ふつうのキャプションとして照合する）。
- 図・表を含まないテキストボックス（囲み）の文字と、Word の文末脚注は、今は XML に出力しない（除外としてレポートの 6 章に載せ、
  冒頭と 14 章に「要確認」として知らせる。4.3）。本文の外（引用文献の段落、和文の冒頭の誌名・副題の段落など。冒頭の最後のセクション区切りの段落は除く。6.1）に結び付いた図形の中身は、
  その領域の段落として扱われ（6.1）、中の画像は出力できない（画像の出力漏れとして要対応で知らせる。4.3）。
  どれも修正計画（`docs/FIX_PLAN.md`）の E・F で直す。
