# 設計

## 1. 目的と最優先の要件

- 入力: 『全国数学教育学会誌 数学教育学研究』のテンプレート（`tests/fixtures/JASME_template_20261009.docx`）で作成された論文の docx
- 出力: J-STAGE 全文 XML（JATS 1.1 Journal Publishing、FULL-J）と、J-STAGE のアップロード用フォルダ構成の ZIP、変換レポート
- **最優先: docx の本文の文字を 1 文字も変えない**（誤字脱字も直さない）。リンクの誤りは許容されるが、少ないほどよい。
  受け取った docx が出版版と違うときのために、先に出版版 PDF から校正の直しと組版の違いを補った docx を作ってから変換する作り方も
  選べる（4.4 のルート2）。そのときも、docx → XML の処理は同じで、XML は（補った）docx の文字と 1 文字も違わない。

## 2. 実行環境の選択（Google Colab）

| 案 | 利点 | 欠点 |
|---|---|---|
| **Google Colab のノートブック（採用）** | ブラウザと Google アカウントだけで動く。ノートブックが毎回 GitHub から最新のコードを入れるので、コードの写しが散らばらない。ファイルは利用者自身の一時的な実行環境で処理される | 実行のたびに準備（1〜3 分）が要る |
| Web アプリ（Streamlit 等を常時公開） | 最も簡単に使える | サーバーの維持・費用・管理者が必要。未公開原稿を外部サーバーに上げることになる |
| GitHub Actions で変換 | 記録が自動で残る | 原稿をリポジトリに置く必要がある（公開リポジトリでは不可） |
| **Colab の中の 1 画面アプリ（Gradio。`app.py`。採用。0.27.2）** | 上と同じ環境で、入力欄・結果・ダウンロードが 1 つの画面に収まる。セルを順に押す操作が要らない | Gradio の版を固定して確かめる必要がある。Colab の iframe の中で動かす |
| 配布用の実行ファイル | オフラインで動く | OS ごとの作成・更新が必要。EMF 変換の LibreOffice を同梱できない |

変換の本体は Python のパッケージ（`src/jasme_jats/`）で、Colab のノートブックはその薄い操作画面にすぎない。
同じパッケージがパソコンのコマンドラインでも、GitHub Actions のテストでも動く。

## 3. 処理の流れ（`pipeline.py`）

1. **読み取り**（`docx_reader.py`）: docx の XML を直接読み、段落を「アトム」（文字・数式・画像・脚注参照・生成文字）の列にする。
2. **構造化**（`structure.py`。構造の型〈`ArticlePlan` とノード〉は `article.py`）: スタイル名から段落の役割を決め、題目・著者・本文（章節項）・図表・注・文献・英文要旨・資料の構造（`ArticlePlan`）を組み立てる。
   スタイルが想定外の段落は、番号の形式などから機械的に推定し、`Decision` として記録する。
3. **機械的リンク**（`linker.py`, `refparse.py`）: 図・表・数式・注・引用文献・URL・DOI。
4. **AI 補完（任意）**（`ai_assist.py`）: AI が返した操作を検証し、構造の組み直しとリンクの追加として適用する。
5. **XML の組み立て**（`builder.py`, `emit.py`）
6. **文字の不変性チェック**（`fidelity.py`）… AI 補完を行った場合も必ずここで行う
7. **最終出力の再チェック**: 目印を取り除いた XML を直列化して読み直し、文字列が検証済みの木と一致することを確かめる
8. **DTD 検証**（`validate.py`）: 同梱の J-STAGE 指定 DTD
9. **画像の出力漏れの検出**（`pipeline.lost_images`）: docx の画像のうち、XML に出力しなかったものを調べる（4.3）
10. **J-STAGE のアップロード時チェック**（`jstage_rules.py`）: 記事アップロードメッセージ一覧のうち、XML だけで判定できるもの（6 章）。
   画像の名前を使うので、実際には 11 の画像の書き出しの後、ZIP を作る前に、出力した画像の名前で行う
11. **画像・ZIP・レポート**（`images.py`, `package.py`, `report.py`）: アップロード用の ZIP には、今回の変換で作った XML、今回指定した PDF、
   `Graphics/` のうち出力できた画像だけを入れる（`package.upload_entries`）。作った ZIP は読み直して、名前の文字・記事フォルダの外の項目・
   想定外のファイル・0 バイトのファイル・XML があることを確かめる（`package.zip_problems`。6 章）

記事の PDF があれば、4 の AI 補完と 5 の組み立ての後、6 の不変性チェックの前に、docx の段落と PDF の文字を照合する（`pdfmatch.py`。4.4）。
ルート2 で Word の番号（自動番号・脚注番号）の全角・半角を PDF に合わせるときは、照合の後で 5 の組み立てをやり直す。
ルート2（docx から作り、出版版 PDF で補う）では、1 の前に、PDF で補った docx を作り（`pdfdocx.py`）、以降はそれを入力にする。
7〜8 のあと、補った docx が元の docx から組版の違いと報告した校正の直し以外に変わっていないことを、照合・直しとは別の実装で確かめる
（補完の確かめ。`fidelity.verify_supplement`。`Result.supplement`。不合格は要対応で、`Result.ok` も偽になる）。

**利用者への知らせ（`report.actions`）**: 変換の結果のうち、利用者が対処すること・確かめることは、`report.actions(r)` の 1 か所で
`report.Action`（level・key・冒頭の文・14 章の行・Colab の枠の見出しと本文・コマンドラインの文）の一覧にする。レポートの冒頭と
14 章、Colab の枠（`colab.result_boxes`。要対応は赤、要確認は黄。ノートブックでは手順 5・6・8、1 画面版では変換の結果の欄）、手順 8 の止め方、コマンドラインの標準エラーと終了コードは、どれも
この一覧だけで決まる（修正計画の D。後の単位で知らせを足すときも、Action を 1 つ足すだけにし、画面ごとに個別の表示を足さない）。

- level は 2 つ。**要対応**（`report.NEEDS_ACTION`）は、コマンドラインの終了コード 1、Colab の手順 8 でダウンロードの前に一度止める
  （もう一度押せばダウンロードできる）、赤い枠、レポートの冒頭・14 章。**要確認**（`report.TO_CHECK`）は、黄色い枠とレポートの冒頭・
  14 章だけ（終了コードは 0）。`Result.needs_action` は要対応があるか。`Result.ok`（不変性チェック・最終出力の再チェック・DTD 検証が
  合格）の意味は変えない（ok でなければ、必ず要対応がある）。
- 要対応: 文字の不変性チェックの不合格（ダウンロードはできる。決定事項 5(d)）、DTD 検証の不合格、J-STAGE のアップロード時チェックの
  問題（`jstage_issues` と `zip_issues`。`--meta` がなく開始ページがないときも EMSGM230E でここに入る）、AI による補完ができなかった
  （見出しは、手動モードなら「貼り付けた回答を読み込めませんでした」、API モードなら「AI による補完ができませんでした」。決定事項 5(a)）、
  手動モードで AI の回答をまだ貼り戻していない（冒頭は手動モードの説明〈`Result.output_note`〉のままにし、14 章・枠・コマンドラインに
  出す。手順 5 では依頼文の枠を出すので、この枠は出さない。決定事項 5(c)）、AI の回答が途中で切れていた、仮の位置に置いた図表、図の本体が
  見つからない図、画像を用意できなかった図、XML に入らなかった画像、ルート2 で PDF の文字を読めなかった（`Result.pdf_fallback`。4.4）、
  最終出力が XML として読めない・実体の宣言がある（`FidelityResult.final_unreadable`。4.2。文字の差分も同時にあるときは両方を言う）、
  ルート2 の補完の確かめの不合格（`report._supplement_action`。key `supplement`。4.4）。
- 要確認: ルート1 で PDF と照合できなかった、ルート1 の PDF との違い、ルート2 で直さなかった箇所（(B)・(C)）・補った後も残る違い（組版の違いは数えない。枠とコマンドライン
  だけ。冒頭と 14 章は下の固定の案内と行）、別の記事の PDF の疑い（`report.pdf_suspect`: docx の段落の半分以上が PDF に見つからない。
  出版社の実際の PDF でまだ試していないので要確認にとどめる。決定事項 4）、照合に使わなかった PDF の文字（4.4）、囲み（問題文・
  ヒントなど）か図の注記か決められず、文字を出力しなかったテキストボックスと、位置を推定して置いた囲み（6.2。0.24.1 までの「文字だけの
  テキストボックスを出力しなかった」暫定の知らせの代わり）、英文要旨の中の和文と思われる段落と、引用文献などの後ろの資料の見出しと思われる
  段落（6 章の「資料」。どちらも出力は変えずに知らせるだけ）、題目・著者・所属・引用文献の段落の中の改行（Word の Shift+Enter。XML では
  改行の文字のまま。`report._newline_action`。決定事項 13(2)。本文・見出し・表のセルの改行は 10 章の一覧だけ。6 章の「段落の中の改行」）、
  番号が重なる・枝番があるためリンクしなかった図・表の参照（`report._float_ref_action`。key `float_ref`。6 章の「本文の図表の参照」。
  AI の状態〈使っていない・回答待ち・API の呼び出しが失敗した・回答を反映できなかった・使った後〉で文を分け、画面ごとに取れる操作を言う〈`float_ref_ai`。使った後に AI に出し直してもらう操作は、手動モードでは回答の貼り直し〈1 画面版は `REPASTE_KEYS` の `float_ref` で手動の欄が見えたまま〉、API モードではもう一度変換する。囲みか注記か決められなかったテキストボックスの知らせ `textbox_undecided` の AI を使った後の文も同じ）、文字から推定した「注」の扱い
  （`report._fn_guess_action`。key `fn_guess`。6 章の「文字から推定した注の見出し」）。

## 4. 文字を変えないしくみ

### 4.1 文字ポリシー（`ooxml.py` の冒頭）

「docx の文字」は、Word で表示される文字（変更履歴をすべて承諾し、隠し文字を隠した状態）とし、次のように定義する。読み取り（`docx_reader.py`）・
検証（`ooxml.canonical_text()`・`canonical_texts()`。`fidelity.source_texts()`）・ルート2（`pdfdocx.paragraph_units()`・`write_fixed_docx()`）の
3 か所は、`ooxml.py` に置いた規則（段落のつながり `joined_paragraphs()` と、隠し文字の判定 `HiddenRule`）を共有し、文字の取り出しはそれぞれ別の
実装で行う（規則を共有するので、規則そのものの誤りは不変性チェックでは見つからない。規則は `tests/test_reader.py` の単体テストで確かめ、
LibreOffice で変更を承諾・表示した結果と比べた。LibreOffice と違う形は 7 章）。

- 含める: `w:t`、数式中の `m:t`、タブ（`w:tab`・`w:ptab` → タブ文字）、改行（`w:br`, `w:cr` → 改行文字）、`w:noBreakHyphen`、`w:softHyphen`、`w:sym`（Symbol フォントは Unicode に対応付け）
- 含めない: 削除された変更履歴（`w:del`・`w:moveFrom`）、フィールドコード、隠し文字、ページ区切り、ルビの読み、テキストボックス内の段落（別の段落として扱う。
  ただし削除の変更履歴の中の図形の段落は欠番にする。`ooxml.in_deleted_run`。読み取り・検証・ルート2 の `paragraph_units` で同じ。0.29.0 より前は、
  検証が数えて読み取りが読まない形で偽の不合格になった）
- 隠し文字（`ooxml.HiddenRule`。その docx の word/styles.xml から作る。修正計画〈`docs/FIX_PLAN.md`〉の G の規則）: スタイルと既定の書式の
  `w:vanish` は、ECMA-376 の切り替えの性質（toggle property。スタイルで真なら、それまでの状態を反転させ、偽なら変えない）として扱う。
  ランの直接の `w:vanish` があればその値（`w:val="0"` なら表示）、なければ直接の `w:specVanish` なら隠す、なければ文字スタイル
  （`w:rStyle`）の値が真なら段落の状態を反転（偽か指定がなければ段落の状態のまま）。段落の状態は、既定の書式（`w:docDefaults`）の値を、
  段落スタイル（`w:pStyle`。なければ既定の段落スタイル）の値が真なら反転したもの（両方にあれば見える）。スタイルの値は `w:basedOn` を
  たどり、`w:vanish` を最初に指定しているスタイル（いちばん派生した側）のもの（派生の連鎖の中では反転させない。循環は打ち切る）。
  暫定（Word では未確認。LibreOffice と違う形は 7 章）。扱わないもの: 数式の中のラン（`m:r`）・表スタイル・
  番号の書式（`w:lvl/w:rPr`）の `w:vanish`、段落記号の `w:vanish`（スタイル区切り）、リンクスタイル（`w:link`）の特別な扱い、テーマ・互換性の設定。
  隠し文字のランの中のテキストボックス（行内・浮動配置）の段落は、ランの隠し文字を継がず、別の段落としてその段落自身の規則で決める
  （3 か所とも。隠し文字のランの中の画像は読み取りが隠す。7 章）。
  規則が暫定で、不変性チェックも同じ規則で docx の文字を取り出すので、規則が Word と違うと、Word で見える文字が XML から消えても合格する。
  このため、ランの直接の指定（`w:vanish`・`w:specVanish`）ではなく、スタイル・既定の書式で隠した文字・画像（`HiddenRule.run_hidden_by` が
  `"style"`。読み取りが `Document.style_hidden`・`ImageRef.hidden_style` に記録する）は、レポートの 6 章に一覧を出し、要確認
  （`report._style_hidden_action`。空白だけの文字は数えない）で知らせる（Word で表示されないことを利用者に確かめてもらう）。
  ランの直接の指定だけで隠した文字は、0.25.0 までと同じく 6 章に載せるだけ。
- 段落の区切り（`ooxml.joined_paragraphs()`）: 段落記号が変更履歴で削除された段落（`w:pPr/w:rPr` の `w:del`・`w:moveFrom`）は、承諾した状態と
  同じく、同じ親の中で次の兄弟の `w:p`（間のしおり・コメントの範囲などの中身のない目印は飛ばす）とつないで 1 段落にする（3 段落以上の連鎖も）。
  段落の ID は連鎖の最初の段落のもので、後ろの段落の ID は欠番（読み取りの段落も、検証の文字もない）。次が表・コンテンツコントロール・カスタム XML
  など段落でない要素のときと、親（本文・表のセル・テキストボックス・注・コンテンツコントロール・カスタム XML）の最後の段落のときはつながず
  （`unjoined_deleted_marks()`）、文字のある段落ならレポートの 10 章の警告に出す（LibreOffice はコンテンツコントロール・カスタム XML の境目でも
  つなぐが、Word では未確認なので、文字が失われない側〈つながない〉を採る）。段落記号の `w:vanish`（スタイル区切り）・`w:ins` はつながない。
  つないだ段落の書式（スタイル・番号・揃え）は、連鎖の中で文字のある最初の段落のもの（すべて空なら最後の段落のもの。「前の段落が空なら後ろの
  段落のもの、そうでなければ前の段落のもの」を先頭からたたみ込んだもの）、セクションの区切りは最後の段落のもの。自動番号は連鎖ごとに 1 回だけ
  数える。スタイルの違う段落をつないだときは判断の一覧（4 章）に記録し、つないだ段落の一覧をレポートの 6 章に出す。
- 変更履歴で削除された表の行（`w:trPr/w:del`）: 行のどの段落にも文字（画像・数式・注の参照も）がなく、図形も読まなかった行は、承諾した状態と
  同じく読み飛ばして記録する（`Document.deleted_rows`。レポートの 6 章）。文字の残る行は出力して 10 章の警告に出す。変更履歴で削除されたセル
  （`w:tcPr/w:cellDel`）は、読み飛ばすと表の形が変わる（LibreOffice は承諾すると列ごと消した）ので出力し（削除された文字は出さない）、10 章の警告に
  出す。読み飛ばす行の段落の docx の文字は空なので、検証（`verify` は文字が空の段落を数えない）は何もしなくても同じ結果になる。
  読み飛ばした行の中の自動番号は数えない（承諾すると行ごと消え、後ろの番号が詰まる）。行の中の隠し文字・つないだ段落・警告も、出力した
  段落の記録には残さない（行ごと、読み飛ばした行として記録する）。すべての行を読み飛ばした表は、キャプション（docx の文字）と空の表
  （空の `<td>` を 1 つ）のまま出力し、10 章の警告に出す（承諾すると表が消える。`builder.Builder.all_rows_deleted`）。6 章の一覧では、
  文字の残らない表をキャプションの冒頭で示す。
- Word が自動生成する文字（自動段落番号・脚注番号）は docx の文字ではない。XML では「生成文字」として区別し、レポートに記録する。
  自動番号の定義が番号付けスタイルを経由する（`w:numStyleLink`）ときは、styles.xml の番号付けスタイルの `numPr/numId` → その `num` の
  `abstractNum`（`w:styleLink`）の順にたどる（`numbering.Numbering._follow_style_links`。循環・見つからないときは番号なし）。
  docx にない注の見出し（Word の脚注機能・文末脚注機能で書かれた注）を補う場合も、生成文字として区別する（6 章の「注」）。

### 4.2 変換中の目印と照合

- 中間表現は、段落の文字をアトムの列として持つ。リンク付けはアトムに `LinkSpec` を付けるだけで、文字列は変えない。
- XML の組み立てでは、段落の文字を必ず `<jx:span src="段落ID" seq="n">` の中に書く（`tracking.py`）。
- `fidelity.verify()` は、docx から **別の実装**（`ooxml.canonical_text()`）で段落ごとの文字列を取り出し、XML の `jx:span` の文字列と比較する。
  - すべての段落が、XML に出力されているか、出力しない理由（`Exclusion`）が記録されているか
  - 目印の外に文字がないか（docx にない文字の追加の検出）
  - 構造の区切りとして落とした文字（`jx:drop`）が空白だけか
  - 同じ段落を二重に出力していないか（同じ `seq` の重複を直接検査する。`seq` の違う二重は文字の不一致として見つかる。空の目印の二重は見つからない）
  - 出力した段落が、出力しない段落（`Exclusion`）にも記録されていないか（レポートの「出力しなかった文字」と食い違う）
  - 空白だけの段落として記録した除外（`Exclusion.blank`）の docx の文字が、本当に空白だけか（同じ段落の除外が 2 件以上あっても、すべて確かめる）
  - 上の 2 つに当たるものは、レポートの 5 章に「変換ツールの不具合」として出し、不合格にする
- 照合後に目印を取り除き（タグを外すだけ）、直列化した最終出力を読み直して、文字列が一致することを `final_check()` で確かめる。
  読み直しが失敗しても例外にせず不合格にし、実体の宣言（`<!ENTITY`）があれば（このツールは出力しないので入り込んだもの）解決せずに不合格にする。
  なければ、実体を解決する通常のパーサ（外部実体・ネットワークは読まない）でも読めることを確かめ、読めなければ不合格にする
  （`FidelityResult.final_unreadable`。要対応。`validate` は `resolve_entities=False` なので未定義の実体参照を検出しない）。
  未定義の実体参照は文字の差分に数えない（読めない側の不備として扱う）。文字の差分は `final_differs`。
- `tests/test_fidelity.py` で、わざと文字を変える・段落を消す・文字を足す・段落を二重にする・出力した段落を除外にも記録する・
  文字のある段落を空白だけとして除外する、などの改変がすべて検出されることを確かめている。

### 4.3 出力しない文字・落とす空白・生成文字

- 出力しない段落（`Exclusion`）: テンプレートの誌名行・装飾行（❚❚❚）、空白だけの段落、重複する所属、図表の一部とみなしたテキストボックスの文字、図に重ねた注記とみなした（または囲みか注記か決められなかった）文字だけのテキストボックスの文字など。レポートに全文を載せる。
  空白だけの段落（全角空白だけのものも）は `ArticlePlan.exclude_blank()` で記録する（理由「空白のみの段落」、`blank=True`）。
  図の画像だけの段落にある空白も `blank=True` で記録する。画像と文字が同じ段落を図に組むときは、文字を除外せず、
  画像だけを図に移して、段落は図の直後に本文の段落として出す（`structure.Classifier.float_mechanical`・`float_from_spec`）。
- 段落記号の削除でつないだ段落の後ろの段落（4.1）は、「出力しない段落」ではなく、前の段落に続いた段落として扱う（ID は欠番で、読み取りにも
  検証にも段落がない。除外には記録しない）。変更履歴で読み飛ばした表の行の段落（文字は空）も除外には記録せず、行の一覧をレポートの 6 章に
  出す。隠し文字だけの段落（段落スタイルで隠した段落など）は文字が空になるので、理由「空白のみの段落」の `exclude_blank` で記録する
  （隠した文字は 6 章の隠し文字の一覧に載る）。
- 付記・謝辞・資料の Word の自動番号の段落は、本文と同じく、同じ番号の定義が続く間 `ListNode`（`<list><list-item><label>番号</label><p>…`）で出す
  （番号は生成文字。0.28.1 までは番号が XML から落ちていた。`structure.Classifier.add_back_para`）。各項目の文脈は、その節の番号のない
  段落と同じ（付記・資料は `<ext-link>`、謝辞は `<uri>`）。見出しの役割（章・節・項見出しのスタイル）の段落は箇条にせず `<p>` で出し、
  番号は生成した文字（`jx:gen`）として先頭に補う（前後の箇条は見出しで別の `<list>` になる）。謝辞 `<ack>` の中の別行数式・表・リストは
  `<p>` で包む（`<ack>` の内容モデルに `disp-formula`・`table-wrap` がないため。`<notes>`・`<app>` は直接置ける）。全行が見出し行の表は
  `<thead>` を作らず `<tbody>` にする（DTD は `thead?, tfoot?, tbody+`）。
- 落とす空白（`jx:drop`）: 姓と名の間（JATS では `<surname>` と `<given-names>` に分けるため）。`split_labels = true` のときは図表番号・章番号とタイトルの間も（注の番号は `<label>` に分けず `<p>` の先頭に書くので対象外。6 章の「注」）。空白以外は落とさない。
- 数式: 根号は、次数（`m:deg`）に文字があれば、次数を隠す指定（`degHide`）が真でも `mroot` にして次数の文字を出力する（`omml.h_rad`）。
  OMML では属性で表される括弧などの記号は MathML の `<mo>` になるため、`jx:implicit` を付けて照合から除く。根号の指数のように MathML で順序が入れ替わる文字は、`jx:o`（docx 上の順序）で並べ直して照合する。
- 画像: 不変性チェックは文字しか見ないので、画像は別に確かめる。組み立ての後に、docx の画像（`Document.images`）のうち、XML に出力した画像
  （`BuildInfo.images`）に入らなかったものを `pipeline.lost_images()` が調べ、`Result.lost_images` に記録する。画像を出力できない場所
  （題目・著者名・所属・引用文献・番号。`emit.Ctx` の `images=False`）の段落や、出力しなかった段落（`Exclusion`）の中の画像がこれに当たる。
  理由は、その段落の文字を XML のどこに出力したか（`jx:span` の祖先の要素）と、除外の記録から推定する。変換の結果は変えず、要対応として
  レポートの冒頭・9 章・14 章、Colab の赤い枠、コマンドラインの標準エラー（終了コード 1）に出す（対処は、Word でその画像を本文の段落に
  移して変換し直すこと）。隠し文字のランの中の画像（`ImageRef.hidden`）は、隠し文字と同じく Word で表示されないので出力せず、
  レポートの 6 章・9 章に載せるだけにする（スタイル・既定の書式で隠した画像は、隠した文字と同じく要確認でも知らせる。4.1）。
- 文字だけのテキストボックス（画像・表・図表キャプションを含まないもの）は、囲み（問題文・ヒントなど）なら `<boxed-text>` に出し、
  図に重ねた注記（矢印・点の名前など）なら理由「テキストボックス内の文字（図に重ねた注記とみなして本文から除外）」で除外する
  （AI の指定なら「…（AI による補完で図に重ねた注記と判断し、本文から除外）」）。囲みか注記か決められないものは、図の注記を本文に
  混ぜないよう、理由「テキストボックス内の文字（囲みか図の注記か決められないため本文から除外。要確認）」で除外し、要確認として
  知らせる（6.2。決定事項 9(2)）。どの扱いでも、中の空白だけの段落は `exclude_blank` で記録する。図表の入った図形の中の、
  キャプションでも本体でもない段落（図の説明・出典など）は、今までどおり「テキストボックス内の文字（図の一部とみなして本文から除外）」
  で除外し、その件数と対処（本文に必要なら Word でテキストボックスの外に出す）を要確認として知らせる（`report._textbox_figure_text_action`。
  浮動配置でない〈行内・VML の〉テキストボックスの中の文字は、AI の placements では戻せず、set_role で指定できるのは fig_caption・table_caption・
  exclude だけ（キャプションの続きとしてなら出せるが、本文の段落には戻せない）。位置を決められない図表の中身は、
  手動モードで AI の回答を貼り戻す前は数えない〈AI がその図表を組めば、図の後ろに本文の段落として出る〉。暫定の判断）。
  0.19.0〜0.24.1 は、テキストボックスの中の、キャプションでも本体でもない文字（文字だけのテキストボックスの文字も含めて）をすべて
  この理由で除外し、その件数を暫定の知らせ（要確認）で出していた。0.25.0 では、文字だけのテキストボックスを上のとおり扱い、
  暫定の知らせは、図表の入った図形の中の除外の知らせに置き換えた。
- Word の脚注・文末脚注のうち、本文から参照されていないもの（参照が削除の変更履歴の中にだけあるものも）は出力せず、理由
  （「Word の文末脚注 5（本文から参照されていない注）」「…（本文の参照が変更履歴で削除された注。Word で変更をすべて承諾すると消える）」）
  を付けて除外する（空白だけの段落は `exclude_blank`。`structure.Classifier.attach_word_notes`）。参照された注の空白だけの段落は、
  注の中に出力する。参照のある段落が XML に出力しなかった段落（誌名の行など）だけでも、注は出力する（6 章の「注」）。

### 4.4 出版版 PDF との照合と、2 通りの作り方（`pdfmatch.py`, `pdfdocx.py`）

受け取った docx が、著者校正を経た最終版とは限らない（組版で印刷所がかっこ・句読点を全角にそろえる、校正の直しが docx に戻されていない
など）。J-STAGE では PDF と全文 XML の両方が公開されるので、XML の本文が PDF と違えば、同じ記事に 2 つの版が並ぶことになる。
そこで、記事の PDF があるときは docx の段落と PDF の文字を照合する。**PDF から XML を作るのではない**
（構造はすべて docx のスタイルから決める。PDF からではスタイルが使えず、組版の都合の文字も混じる）。

作り方は 2 通りで、最初に利用者が選ぶ（Colab の手順 2 の `ROUTE`、コマンドラインの `--route`、`Options.route`）。
Colab の初期値はルート2（PDF がないときは利用者がルート1 を選ぶ）。コマンドラインは `--pdf` があればルート2、なければルート1 が既定。
`Options.route` の既定は、PDF がなくても動くようにルート1（`"docx"`）。

- **ルート1「docx から作る」**（`route="docx"`）: docx の文字のまま XML にする。PDF があれば照合して、違いをレポートの 13 章に
  載せるだけ（冒頭とチェックリストにも件数を出す）。docx を直して変換し直すか、ルート2 で変換し直すかは人が判断する。
- **ルート2「docx から作り、出版版 PDF で補う」**（`route="pdf"`。PDF が必須）: Word の文字が正で、出版版 PDF（印刷所の校正を経た
  もの）からは著者校正の直しを補う。違いを (A) 組版の違い・(B) 校正の直し・(C) 決められない違いに分け、(A) と (B) を PDF に合わせた
  docx（`巻_開始ページ_PDFで補完した原稿.docx`。Word の変更履歴つき。作成者名「jasme-jats（出版版 PDF による補完）」。入力が同名のときは
  `_2` などの別名）を先に作り、
  それをルート1 と同じ処理で変換する。補った docx は出力フォルダに置く（Colab では手順 8 でダウンロードする「変換結果」の ZIP に入る）。
  Word で開いて変更を 1 つずつ確かめ、却下したい変更があれば、却下して保存した docx をルート1 で変換し直す。
  最後に補完の確かめ（下の「補完の確かめ」）で、補った docx が元の docx から (A) と報告した (B) 以外に変わっていないことを確かめる。PDF の文字を読めないとき（画像だけの PDF、壊れた PDF、pypdfium2 が
  入っていないとき）は、変換を止めずに、元の docx をそのまま変換し（結果はルート1 と同じ。補った docx は作らない。補完の確かめも行わない）、要対応
  「出版版 PDF で補えませんでした」として知らせる（`Result.pdf_fallback`。Colab の赤い枠、レポートの冒頭・14 章、
  コマンドラインの終了コード 1。修正計画の決定事項 4）。ルート1 で PDF を読めないときは、要確認「出版版 PDF と照合できませんでした」。

照合（`pdfmatch.py`。どちらのルートでも同じ）:

- PDF の文字（pypdfium2）から、空白とページ番号を除いた列を作る（`pdf_stream`。次の項目）。docx の全段落（表のセル・図の中の文字も
  含む）を docx の順につないだ列と PDF の列を、まとめて照合する（`_joint`）: どちらにも 1 回だけ出る 8 文字の並び（アンカー）の最
  長増加列で単調に（順序を保って）対応させ、アンカーの間を difflib で埋めて、段落ごとの「塊」（PDF の中で続いて一致した部分）にす
  る。単調な対応に入らなかった段落や段落の一部（2 段組みの読み順のずれ、表の後ろに出た段落の最後の行など）は、隣の塊のすぐ隣、次
  （前）の本文の段落のすぐ前（後ろ）、アンカーの順に探す（どれもない短い段落は、前後の段落の間か、段落の一部の文字列が PDF の中に
  1 回だけ出る位置で探す。前後の段落の間では、行全体でしか一致させない行の文字も、行全体が段落の文字の中にあれば使う。くり返し示す
  問題文など、同じ文字の段落の最初の行が何ページにも出る形）。段落の最後（最初）の部分は、表・図・ほかの段落の後ろ（前）に出て、
  校正で一部が直されていても（表の後ろに出た最後の行「…持った。」と docx の「…取った。」）、docx ですぐ後ろ（前）の本文の段落の
  すぐ前（後ろ）の行まるごとが、その部分の文字の半分以上と一致し、最後（最初）の文字も同じなら、その行に置く（`_loose_edge`。間に
  ある照合に使わない行だけの行〈1 ページ目の最後の投稿受付日の行、次のページの最初の柱など〉は 3 行まで飛ばす）。ただし、その
  部分が docx で一文まるごと（段落の最後なら文の終わりの直後から始まり、段落の最初なら文の終わりか読点で終わる。校正で消された
  文や、書き出しの「そこで，」かもしれない）のときは、似た行（すぐ後ろの図の中の「問題を解きなさい。」と、消された「その問題を
  示す。」）に一致した文字だけで置くことはしない（置くと、図の中の文字で docx の文字を置き換えてしまう）。段落の最後（最初）の
  docx の文字がどの塊にも入らないときは、段落の最後（最初）の行の 1〜2 文字の一致も、偶然の一致として外して探し直す（段落の
  最後の数文字が小さな図の後ろに出たとき、図の中の行「前時の表を振り返る」のよく使う文字「時」「を」が、段落の最後の
  「時間を取った。」と並べられ、図の中の文字「の表」で docx の文字を置き換えないように）。
  段落ごとに照合する PDF の窓（`_window_lines`。列の位置のリスト）は、
  段落の塊のある行と、そのすぐ前後の照合に使わない行（柱の候補の行など）で作り、ほかの段落の塊の文字は入れない。2 つの段落の塊が同
  じ行にあるときは、行の始まり・終わりを段落の境目にしやすくして境目を決め直す（`_contests`。校正で消された段落の最後の文字が、次
  の段落の書き出しと並べられないように。行の境目の点は、1 文字の一致より小さくする〈次の段落の書き出しの 1 文字を前の段落のものに
  しないように〉）。境目の候補が同じ点で 2 つ以上あるとき（間の文字が、校正で直された・足された、どちらの段落の docx の文字とも
  一致しない文字のとき。docx では 2 つの段落が、PDF では 1 つにつながったものや、追い込みの見出し）は、文の終わりの直後、同じ行の
  中の全角の空白の直前（追い込みの見出しと本文の間）の順に決める（「確かめる」→「確かめた。」の「た。」を、次の段落の頭に
  足さない）。決められなければ、どちらの段落の最初・最後の違いも直さない（`EDGE_WHY`。間の文字は両方の段落の 13 章に出す）。
  前の段落の最後の直し（「確かめる」→「確かめて」）と、前の段落の最後の削除と次の段落の書き出しの挿入（「る」を消して
  「そこで」を足す）は PDF から区別できないので、docx の直された文字がどちらの段落にあるかでは決めない（決めると、片方の形で、
  次の段落に足された語を前の段落に足し〈「…確かめそこで」〉、次の段落の語を落とす）。
  段落ごとの照合（`_align`）では、全角・半角、大文字・小文字、ハイフン・ダッシュの違いは無視して位置を合わせ、段落の途中の、PDF の 1 行の中だけの 1〜2 文字の一致（docx にない表のキャプションの「表１」の「１」と docx の
  「12点」の「1」など。`_line_islands`）と、投稿受付日の文字列の一部だけとの一致（`_date_islands`）は、偶然の一致として外して照合

  同じなら読まない（速さのため）。段落記号・書式（`w:rPr`）にかかるこのツールの変更履歴は不合格。(2) 段落ごと（段落記号の削除で
  つないだ段落は 1 つ）に、変わっていない文字をはさまずに続く挿入・削除を 1 つの単位にし、(3) 単位を、1 文字ずつの (A) の対・空白の削除と、
  その段落の報告した `text` の `Fix`（古い文字・新しい文字が文字列として一致するもの）の並びで説明する。位置（`Fix.start`）は使わない
  （数式の後ろで読み取りと検証の位置がずれるため）。説明できない単位と、どの単位にも当たらない `Fix` は不合格。(4) Word が付ける番号
  （`plan.pdf_numbers`）が、元の文字列と 1 文字ずつ同じか全角・半角か `NUMBER_PAIRS` の対か。不合格は要対応（`Result.ok` も偽、終了コード 1、レポートの 1 章・13.8）。不合格の箇所を自動で直さない（ツールの不具合を
  隠さないため）。限界: 変更履歴の単位の中で (B) の文字列が `Fix` と違う並びになる形、1 つの単位に (B) が 16 を超える形、隠し文字のランの
  中の注の参照の隣の空白の削除は、偽の不合格になりうる（安全側）。

## 5. AI 補完の設計

- AI には XML も docx も直接編集させない。AI が返すのは操作の一覧（JSON。`ai_assist.RESPONSE_SCHEMA`）だけ。
- 操作の種類: `link_citation`（年の部分のみ）/ `link_figure` / `link_table` / `link_note` / `link_formula` / `set_role` / `formula_image` / `split_name`
- プログラムによる検証（`apply_ops`）:
  - 対象の段落・文字列（完全一致）・リンク先が存在するか
  - 引用文献へのリンクの文字列が「年」か（利用者の指定した規則を機械的に強制する）
  - 数式・画像をまたがないか、既存のリンクと重ならないか
  - 役割の指定がその位置で可能か（`ai_assist.set_role_problem`。下の「set_role の可否」）
  - MathML が MathML の要素だけでできているか（それ以外の要素は不採用、未知の属性は除去）。DOCTYPE、実体参照・コメント・処理命令（要素でない
    ノード）がある MathML も不採用（`parse_mathml`。実体参照が出力に入ると、DTD 検証は通っても XML として読めない）
  - 回答の項目の型（`split_ops`）: 文字列にできない値（一覧・辞書・bool）は理由付きで不採用にし、`None` は空文字、数値は `str()`
    にして照合に使う（`mathml` だけは XML に書く項目なので数値も不採用）。`placements` の `float`・`after`（`None` も可）と `items` の
    `caption`・`body` の要素の型も確かめる（偽の値は空の一覧として通す）。`notes` は一覧か文字列だけ使い（数値は `str()`）、それ以外は捨てて
    使わなかった旨の注意を `notes` に足す（1 文字ずつの気づきにしない）
  - リンクの操作（`link_*`）の対象の段落が、題目・副題・著者名・所属・引用文献（`plan.no_link_paras()`）や別行数式の段落でないか
    （XML にリンクが出せない文脈なので不採用。`split_labels` のときの図表の番号の `<label>` の部分〈`label_ranges`〉も不採用）
  - `formula_image` を指定した図に、表・移した画像・キャプションの続き（2 段落目以降）がないか（あると表の文字が落ちるので不採用）
  - AI が `link_figure`・`link_table` でリンクを付けた参照は、`plan.float_unlinked`（番号が重なる・枝番があるためリンクしなかった参照。
    要確認 `float_ref`）から除く（図か表・段落 ID が同じで、参照の範囲〈`UnlinkedRef` の `start`・`end`。段落の文字の中の位置〉が AI のリンクの範囲と重なるものだけを除く。リンクの対象でない同じ文字〈「地図1」の「図1」〉に AI がリンクを付けても、本当にリンクされていない参照は残る）。AI を使った後の `float_ref` は、AI もリンクを
    付けなかった参照だけを挙げる
  - 姓 + 名 が氏名の文字列と一致するか
- 位置を機械的に決められなかった浮動配置の図表（6.1）は、`operations` とは別の `placements` で、図形ごとに置く位置（`after`: その直後に置く段落）と
  中身の組み合わせ（`items`: 図・表ごとのキャプションの段落と本体）を必ず指定させる。回答の JSON は `placements` を最初に書かせる
  （`RESPONSE_SCHEMA` の順、`SYSTEM_PROMPT`、手動モードの依頼文の見本・項目の説明・回答の書き方。回答が長すぎて途中で切れても、
  位置の指定が残るように）。検証（`float_placements`）:
  - 図形が「位置を決められなかった図表」にあるか（機械的に配置した図形は変更させない。依頼文でも「変更不可」として示す）
  - `after` が本文の段落か（図形の中の段落・表のセル・本文以外は不可）。本文の外（注・引用文献・付記・謝辞・英文の部分・資料。
    `structure.AFTER_BODY_REGIONS`）の段落を指定したものも採用しないが、その図表は本文の冒頭ではなく本文の最後に仮に置く
    （決定事項 21。不採用の理由にもそう書く。同じ図形に後ろで正しい指定があれば、そちらを採用する）
  - キャプション・本体が、その図形の中の段落・表・画像か。本体の段落に画像があるか（文字だけの段落を図の本体にすると落ちるため。
    画像と文字が同じ段落は本体にでき、画像を図に入れ、段落は文字ごと図の直後に本文の段落として出す。6.1）
  - 同じ中身を 2 回使っていないか、表を「表全体」と「セルの段落」の両方で使っていないか
  - 指定に含まれなかった中身は、図表の後にそのまま出す（文字を落とさない）
- **set_role の可否**は `ai_assist.set_role_problem(p, plan, role)` の 1 か所で決め、回答の検証（`role_overrides`）と、依頼文の
  「出力から除外」の一覧の案内（`set_role_hint`）の両方で使う（修正計画の N6。0.23.1 までは、冒頭・著者表・Word の注の段落にも
  「本文の一部なら set_role を提案」と書き、必ず捨てられる set_role を AI に勧めていた）。上から順に見て、最初に当たった理由で
  採用しない: 役割の名前が一覧にない、図形の中の段落（`float_id`。`placements` で指定させる）、Word の脚注・文末脚注の段落（参照の
  ない注を含めてすべて。注の区切りは Word のとおりにする）、領域のない段落（冒頭・後付け・英文の部分の表のセルなど）、英文の
  題目・副題の段落（変えると英文の題目・副題が XML から落ちる）、`app_heading` を英文要旨・資料以外の段落に指定した、
  その領域（`plan.region`）で指定できない役割（`ai_assist.REGION_ROLES`）。注の一覧の段落では、`fn_start`（新しい注の始まり）と
  `p`（前の注の続き）で注の区切りを指定できる。英文の部分では、`app_heading` で資料の始まりを指定でき（英文要旨に入った資料の
  和文の段落など）、資料の見出しに `abstract` を指定すると、その見出しから次の資料の見出しまでが英文要旨に戻る（誤って資料にした
  見出しのスタイルの段落など）。資料の見出しに `p` を指定すると、資料の中の段落になる（前の資料の続き。前に資料がなければ、
  見出しのない資料〈`<app>` の `<title>` が空〉の最初の段落。資料の文字を英文要旨に入れないよう、英文要旨に戻すのは `abstract`
  だけにする）。ただし、`abstract` で英文要旨に戻した後ろの段落のうち、資料の見出しの形でも見出しのスタイルでもない段落への
  `p` は、資料を始めず英文要旨のままにする（`abstract` の「次の資料の見出しまで英文要旨」の意味のとおり。同じ回答で、戻した
  見出しの後ろの段落にも `p` が付いたときに、その段落から見出しのない資料が始まらないように。判断の一覧には「英文要旨の段落の
  ままにした」と記録する）。
  依頼文の案内は、`p` を指定できる段落には「本文の一部なら set_role を提案」、ほかの役割だけを
  指定できる段落にはその役割（冒頭の段落なら「title, subtitle」）、どれも指定できない段落には「この段落の役割は set_role では
  変えられない」と書く。浮動配置でないテキストボックス（行内・VML）の段落（`textbox_id` があり `float_id` がないもの）には、
  `fig_caption`・`table_caption`・`exclude` だけを受け付け、ほかの役割は「囲みか図の注記かは placements の kind box・label で指定する」
  として採用しない（修正計画の F の (1)。VML のキャプションへの `fig_caption` は今までどおり効く）。浮動配置の図形の段落（文字だけの
  テキストボックスを含む）は、今までどおりどの役割も placements で指定させる。ただし、囲みとして位置を機械的に決めた文字だけの
  テキストボックス（下の placements でも変えられないもの）の段落には、placements を案内せず「囲み（boxed-text）として扱いと位置を
  機械的に決めたので、変更できない」と返す（浮動配置でないものの `fig_caption`・`table_caption`・`exclude` は受け付ける。案内が
  行き止まりにならないように。F の確かめで直した）。囲み・図の注記の判断の対象でないテキストボックス（`plan.textboxes` にないもの:
  図表の入ったテキストボックス、本文の外・表のセルの中のものなど）の段落にも、placements を案内せず「囲み・図の注記の判断の対象で
  ない…ので、段落に指定できる役割は fig_caption・table_caption・exclude だけ」と返す（placements にも指定できないため。F の点検の
  1 回目で直した）。依頼文の案内は、囲みか図の注記か決められなかったテキストボックスの段落には
  「囲みなら placements の kind box、図の注記なら label で指定」、図に重ねた注記とみなしたテキストボックスの段落には「図の注記でなく
  本文の文章なら、placements の kind box で囲みに指定」と書く（ほかは、set_role で指定できる役割だけを示す）。
- 文字だけのテキストボックス（6.2）も `placements` で指定させる。`float` にテキストボックスの ID（x1 など）、`items` に
  `{"kind": "box" か "label", "caption": [], "body": []}` を 1 つだけ書く（box は本文の囲みで、`after` の段落の直後に置く。label は図に
  重ねた注記で、本文に出さない。`after` は使わない）。指定できるのは、囲みか図の注記か決められなかったもの（box か label。依頼文の
  「# 囲みか図の注記か決められなかったテキストボックス」。すべて指定させる）、位置を推定した囲み（box で位置だけ。「# 位置を推定した
  囲み」。違うときだけ）と、図に重ねた注記とみなしたもの（box で本文の囲みに戻すだけ。「# 図に重ねた注記とみなして除外した
  テキストボックス」に中身と判定の根拠を載せ、本文の文章のときだけ指定させる。暫定の判断。F の確かめで、図の近くの短い問題文が
  注記とみなされると AI でも戻せないことが分かったため）。囲みとして位置を機械的に決めたもの（「# 囲みとして位置を機械的に決めた
  テキストボックス（変更不可）」）と空白だけのもの、2 回目の指定、items が 1 つでない・kind が box・label でない、caption・body が
  空でない、位置を推定した囲みと図の注記とみなしたものへの label、box の `after` が本文の段落でない指定は採用しない
  （`ai_assist._box_placement_problem`）。AI が囲みにした判断の文には、機械的な判定（「機械的には図に重ねた注記と判断していた」
  など）も書く。採用した指定の判断（category box）は `plan.float_decisions` に入り、2 章の採用の
  一覧に place_float として載る。組み直した後に `after` が本文の段落でなくなった指定と、同じ回答の `set_role` で中の段落を図表
  キャプション・除外にして文字だけのテキストボックスでなくなったものへの指定は、指定なしに戻し（決められないものは除外のまま
  要確認）、2 章の不採用の一覧に載せる（`pipeline.convert`。黙って捨てない）。浮動配置の図形（s1 など）に kind box・label を書いたものは「items の kind は fig か table」で採用しない。依頼文の段落一覧
  では、文字だけのテキストボックスの段落の場所を「テキストボックス x… の中」と書く（浮動配置の図形の中でも x の ID で示し、浮動配置の
  ものは「テキストボックス x…（浮動配置）の中」として、set_role ではなく placements で指定するものだと分かるようにする）。
- `set_role` または `placements` を含む場合は、docx を読み直して構造を最初から組み立て直してから、他の操作を適用する。
  組み直すと図表の並びが変わって ID（F1 など）がずれることがあるため、AI が依頼文の ID で指定したリンク先は、キャプションなどの段落 ID を目印にして組み直した後の ID に読み替えてから適用する（`target_keys` / `retarget_ops`）。
  `fn_start` で新しく分けた注は依頼文に ID がないため、`link_note` のリンク先はその注の最初の段落の ID で指定させ、組み直した後の注の ID に読み替える。
- 位置を決められない図表は、AI に渡す前の組み立てではアンカー段落のすぐ後ろに仮に置くが（6.1）、依頼文の段落一覧は docx の順で、位置の手がかり（アンカー段落・距離・行数の推定）も docx の記録から作るため、仮の位置は AI の判断に影響しない（依頼文の図表の ID と、推定の「指定がなければ…に仮に置く」は仮の位置で決まる。リンク先は組み直した後の ID に読み替える）。
- 回答の JSON の前後の文字（前置きの説明や、閉じの ``` のないコードブロックの後ろの説明など）は使わず、最初の `{` から最後の `}`
  までを読む（`parse_response`。後ろの文字に `}` があるとき〈JSON が 2 つ続くときなど〉は読めない回答とする）。コードブロックは、
  ```（json）のすぐ後ろが `{` のものだけを使い、閉じの ``` は行の頭にあるものだけとみなす（`_json_text`・`RE_FENCE`。JSON の文字列の
  中の ``` は改行を含められないので行の頭に来ない）。回答が `{` で始まるとき（コードブロックの中身だけをコピーしたときなど）は、
  コードブロックを探さずに回答全体を読む。
- 途中で切れた回答（API の出力の上限、チャットの回答の途中までの貼り付け）は、JSON の読み取りの誤りが回答の最後で切れた形
  （文字列の途中で終わった「Unterminated string」、または「Expecting …」の後ろが空か値の書きかけ。`cut_at_end`）のときだけ、
  最後まで書かれた `placements` の要素を読む（`parse_cut_response`。最上位のキーと値、`placements` の要素を 1 つずつ JSON として
  読み、途中で切れた要素とその後ろは読まない。閉じ括弧を補ったり推測で直したりはしない。`operations` と `notes` は、最後まで
  書かれた要素があっても使わない）。読めた指定も、ふつうの回答と同じく検証する。反映したときは、読み取りの誤りにはせず、
  要対応（AI に出し直してもらう）としてレポートの冒頭・2 章・14 章、Colab の枠、コマンドラインに出す（`AIOutcome.partial`）。
  `placements` に届く前に切れた回答と、途中の書き損じ（飾りの引用符など）の回答は、今までどおり読めない回答として扱う
  （読み取りの誤りには、回答の最後で切れた形なら「途中で切れている可能性」〈最初から出し直してもらい、続きだけを貼り付けない
  よう案内する〉、飾りの引用符なら出し直しの頼み方の案内を付ける）。最後まで書かれた回答の書き損じは、途中で切れた回答として
  読まない: 最後の文字列の閉じだけが飾りの引用符の回答（「Unterminated string」になるが、切れた文字列の中に、すぐ後ろが
  「,」「]」「}」「:」の飾りの引用符がある。`cut_at_end`。文字列の中の「“主張”について」のような飾りの引用符は JSON の文字として
  正しいので、切れた形とみなす）と、閉じの ``` まで書かれたコードブロックの中で JSON が途中で終わっている回答。
- 数式画像は、元の画像を残したまま AI が読み取った MathML を `<alternatives>` で併記する。これは docx の文字ではないため `<jx:ai>` で囲み、
  不変性チェックでは「追加」と扱わず、レポートに別枠で一覧を出す。DTD に合わない場合は自動で取り消す。
- API モードと手動モードは、依頼文の作り方と回答の受け取り方が違うだけで、検証・適用・最終チェックは同じ。
- 依頼文の「機械処理で解決できなかった箇所」には、リンク先が見つからなかった参照（3 章と同じもの）、判断の一覧のうち段落の役割・
  数式・図・表・注・囲みの記録（「推定:」の行。リンクにしなかった上付きの数字・語の中の図表番号の記録には、`link_note`・`link_figure`・
  `link_table` の text と occurrence を書く。6 章）、出力から除外した段落、姓と名の区切りがない氏名（`builder.BuildInfo.unsplit_names`
  の段落の ID・前後の空白を除いた氏名・言語。4 章の記録の文言から切り出さない。氏名の中の改行は「⏎」で示す。英文の氏名も、決定事項 17 で今までどおり載せる。
  `split_name` は和文の氏名にしか使えない〈`apply_ops` が不採用にする〉ので、英文の行には「split_name は和文の氏名にだけ使えるので、
  提案しない」と添える。英文の氏名は、builder が 10 章の警告〈「AI による補完では、英文の著者名は分けられません」〉でも知らせる）を
  載せる（`build_request`）。
- API の呼び出し（Claude）: 既定モデル `ai_assist.DEFAULT_MODEL`、構造化出力（JSON スキーマ）、`effort: high`、ストリーミング、拒否時のサーバー側フォールバック（`fallbacks: "default"`）。
- モデル: 既定は動作確認済みのモデル（`ai_assist.DEFAULT_MODEL`。表示名・料金・提供終了の予定は `ai_assist.DEFAULT_MODEL_INFO`）。指定したモデルが見つからない（提供終了など）ときは、Models API の一覧から最新の Opus を選んで 1 回だけやり直し、レポートに記録する。`auto`（Colab の「自動（最新の Opus）」）では、はじめから最新の Opus を使う。
  既定のモデルは `ai_assist.DEFAULT_MODEL` の 1 か所で決め、表示名・料金・提供終了の予定は `ai_assist.DEFAULT_MODEL_INFO` にまとめる
  （`pipeline.Options.ai_model`・コマンドラインの既定はこれを使い、`tools/make_notebook.py` は ai_assist.py をファイルとして読んで、
  ノートブックの手順 4 の既定と「API キーについての詳細」を作る。修正計画の U5）。
- API モードの入口は `ai_assist.call_provider()`。Claude（推奨・`call_api()`）のほか、ChatGPT（`call_openai()`。OpenAI の Responses API）、
  Gemini（`call_gemini()`。Google の Gemini API）、Sakana AI（`call_sakana()`。Sakana Namazu・Fugu の OpenAI 互換 Chat Completions API、
  接続先 `https://api.sakana.ai/v1`）に対応する。どれも依頼文と画像を渡して JSON の文字列（`AIOutcome.raw`）を受け取るだけで、
  検証・適用・最終チェックは共通。回答は同じ JSON スキーマ（`RESPONSE_SCHEMA`）で受け取る（OpenAI は strict の json_schema、
  Gemini は `response_json_schema`、Sakana AI は `response_format` の json_schema。Sakana AI では受け付けられなければ指定なしで
  1 回だけやり直し、依頼文に入れた回答の形式（見本と項目の説明）で JSON を返させる）。回答が出力の上限で切れたときは、どの AI でも
  切れたところまでの回答を残し（`AIOutcome.raw`・`cut`）、最後まで書かれた `placements` だけを読む（上限で止まっても JSON が
  最後まで書かれていれば、ふつうに読む）。
- OpenAI 互換の接続先（Sakana AI）には、API キーを必ず明示して渡す（環境変数 `OPENAI_API_KEY` の OpenAI のキーを別の会社に送らないため）。
- Sakana AI は既定で送信内容を学習に使う設定なので、ノートブックで選んだときに、学習への利用を止める（オプトアウトする）よう赤い枠で注意する。
- Claude 以外では、モデルを利用者が指定する（既定値を持たない。モデルの入れ替わりが速く、動作確認もしていないため）。
  Claude Opus と同等以上の性能のモデルを推奨する。API キーの作り方などは利用者が各社の案内で調べる（ノートブックでは説明しない）。
- 推奨を Claude とする理由: 依頼文（`SYSTEM_PROMPT`）と回答の検証を Claude で試して調整しているため。他社のモデルでも、誤った提案は
  検証で捨てられるので本文の文字は変わらないが、補完の効果は下がりうる。

## 6. J-STAGE に合わせた主な判断

| 項目 | 判断 | 理由 |
|---|---|---|
| DOCTYPE・ルート要素 | J-STAGE マニュアルの固定値 | マニュアル 3.3.3 |
| 題目 | 本文の言語の題目を `<article-title xml:lang>`、もう一方を `<trans-title-group xml:lang><trans-title>` | J-STAGE は article-title を「タイトル」、trans-title を「翻訳タイトル」として、xml:lang で日・英を判定する |
| 英文要旨 | 和文の論文では `<trans-abstract xml:lang="en">`、英文の論文では `<abstract xml:lang="en">` | J-STAGE では「抄録(英)」（abstract）には「タイトル(英)」（article-title）、「翻訳抄録(英)」（trans-abstract）には「翻訳タイトル(英)」（trans-title）が必要（アップロードメッセージ EMSGM102E/104E）。和文の論文で英文要旨を abstract にすると「英語タイトルがない」エラーになる。ガイドライン 3.1.23 の例も和文論文の英文抄録は trans-abstract。本誌には和文要旨がない |
| 抄録の `specific-use` | 設定ファイルの値（既定 `secondary-disallow`） | 抄録ライセンスフラグ。DTD・ガイドライン上 `<abstract>` にだけ付けられ、`<trans-abstract>` には付けられない（和文の論文では出力されない）。学会の方針で決める |
| 引用文献の `xml:lang` | かな・漢字を含む文献は `ja`、それ以外は `en` | J-STAGE の「引用文献（記述言語）」（未設定だと EMSGM247E） |
| 記事種別・原稿種別 | `<article article-type="other">`（その他）。原稿種別は `<subj-group subj-group-type="article" xml:lang="ja|en">`。Colab の手順 3 で「論文 / Article」「共同研究 / Collaborative Research Report」「講演記事 / oration」「その他（自由入力）」から選ぶ | 学会の指定。選択肢は設定ファイルの `[manuscript_types]`（変えたらノートブックを作り直す） |
| キーワード | 任意。Colab の手順 3 で日本語・英語を別々の欄に入力（「;」「；」区切り）。`kwd-group xml:lang="ja"` と `xml:lang="en"` | docx にキーワードの欄がないため。J-STAGE の上限は日・英あわせて 100 個（EMSGM149E。超えたら手順 3 で止める）。日本語の欄に英語だけのもの、英語の欄にかな・漢字を含むものがあれば、取り違えの確認を促す |
| 査読の有無 | 利用者が必ず入力（Colab の手順 3 で選ばないと先に進めない）。査読ありは `<history><date date-type="approved">`（最終査読日。分からなければ年月日を空に）、査読なしは `<date date-type="accepted as received">`（年月日を空に） | ガイドライン 3.1.30。どちらも書かないと資料の査読あり/なしの設定が引き継がれるため、記事ごとに明示する |
| 登載時チェックの再現 | `jstage_rules.py` で、アップロードメッセージ一覧のうち XML だけで判定できるもの（題目と抄録の言語の対応、日付の前後、所属番号の連番、DOI の文字、画像ファイル名など）を確かめ、レポート 12 章に出す | DTD に合っていても J-STAGE で弾かれる条件があるため |
| 図表番号 | 既定は caption の中に番号ごと入れる | 文字を落とさないため（`split_labels` で切替） |
| 本文の図表の参照 | 「図1」「表2、3」「Figure 1」「図1乃至図2」などを `<xref ref-type="fig|table">` にする（キャプションの段落・引用文献を除く）。「図」「表」の直前の文字が漢字で、「掲」「至」「及」（前掲・乃至・及び。`linker.FLOAT_REF_OK_BEFORE`）でなければ、語の一部（地図1・図表1・発表1回目・概念図1・代表1名・付表1）とみなしてリンクせず、先頭の番号の直後から探し直す（「図表1と表1」の後ろの「表1」、「地図1、図2」の「図2」はリンクする。「地図1、2」の「、2」もリンクしない。直前の 1 文字だけで決めるので、「上図1」「同図2」「右図1」「本表1」のような正しい参照もリンクしない〈7 章〉）。英語の参照（Figure・Fig.・Figs.・Table）は日本語の語の一部にならないので、直前の文字を見ない（「実験結果Fig. 1」もリンクする）。番号の数字が途中から上付きの文字になるとき（「図1」の直後に上付きの注番号「1)」が続くと、段落の文字では「図11)」になる）は、参照を上付きの手前で切る（図1 にリンクし、上付きの文字は「本文の上付きの注番号」の行の規則で扱う〈図・表の番号の直後なので、直前の数字を指数の底とはみなさない〉。並びの番号〈「図1、2」＋上付きの「3)」〉も同じ。番号が上付きの文字で始まるものは切らない。`linker._before_sup`。先頭の番号の途中で切ったときは、上付きの文字の後ろの並びの番号〈「図1¹、2」の「、2」〉はリンクしない〈「図1¹と図2」の図2 は、次の参照としてリンクする。0.26.0 は「図11、2」と読み、「2」を図2 にリンクしていた。番号と並びの間に注番号を置く書き方はまれなので、そのままにした〉）。リンクしなかった参照は、先頭の番号の図・表があるときだけ判断の一覧（4 章。applied=False）と AI 依頼文の「推定:」に載せ、AI の `link_figure`・`link_table` の text と occurrence を書く（要対応・要確認にはしない）。番号の図・表がなければ、記録も 3 章の「見つからない」も出さない。ただし、同じ種類のキャプションの番号が重なる（図1・図1）か、キャプションに枝番がある（図1-1・図1-2、図2.1）ときは、その番号の参照と、番号のすぐ後ろに枝番が続く参照（「図1-2」。枝番のキャプションがない論文の「図1-2」は今までどおり範囲〈図1〜図2〉）を、どの図・表か決められないので**リンクしない**。判断の一覧と `plan.float_unlinked` に記録し、要確認 `float_ref` で知らせる（誤ったリンクを出さない。手でリンクを付けるか、AI による補完で指定させる）。キャプションの番号は `structure.caption_label` が枝番も読む（枝番の区切りは `structure.CAP_BRANCH_SEP`、数字は 1 〜 2 桁で直後に数字が続かないもの〈`CAP_BRANCH_NUM`。「図1―2019年度の推移」は枝番にしない〉。`builder.RE_LABEL_SPLIT`〈`split_labels` のとき `<label>` に分ける番号〉と `linker.RE_BRANCH_REF` も同じ定義）。キャプションの 2 段落目以降（`caption_more`。出典の行など）も、文脈 `caption` でリンクと PDF との照合の対象になる（図表の参照の対象にはならない） | 修正計画の M5・決定事項 16（2026-10）。0.26.0 までは直前の文字を見ず、地図1・付表1・発表1回目などが図・表へのリンクになっていた（1 章の許容するリンクの誤り）。機械処理は迷ったらリンクしない側に倒し、足りないリンクは記録から AI か人が補う |
| 段落の中の改行（Word の Shift+Enter。`w:br`・`w:cr`） | 表のセル（`<td>`・`<th>`）では、改行の前に `<break/>` を補う（改行の文字は `<break/>` の後ろに残す。`<bold>` などの書式の要素の中には置けないので、書式の要素はいったん閉じる。リンクの中には入れない。`emit.Ctx.breaks`）。セルの中の段落と段落の間にも `<break/>` を入れる（0.25.0 まで）。本文・見出し・要旨・キャプション・題目・著者・所属・引用文献の改行は、改行の文字のまま出す。どれもレポートの 10 章に一覧し、題目・著者・所属・引用文献の改行は要確認で知らせる | 決定事項 13。DTD では `<td>`・`<th>` の直下に `<break/>` を置ける（`<p>`・`<bold>`・リンクの中には置けない）。J-STAGE の修飾タグ許容一覧（別紙 1）では、題目・抄録・所属機関名・引用文献の `<break/>` は ×。全文 XML 作成マニュアル 3.5.4 (6) の td・th の文字修飾の一覧に `<break/>` はない（`<xref>`・`<inline-formula>` もないが、前からセルに出している）。J-STAGE の画面での表示は試験登載で確かめる（`docs/JSTAGE_NOTES.md`） |
| 引用文献 | `<mixed-citation>` に原文をそのまま入れ、年・論文名・誌名・DOI・URL にだけタグを付ける | J-STAGE は mixed-citation の文字をそのまま表示する。タグは文字を変えない |
| 文献中の DOI | 既定（設定 `ref_doi = "pub-id"`）は `https://doi.org/` の部分を文字のまま、`10.…` の部分を `<pub-id pub-id-type="doi" xlink:href>` にする。`ref_doi = "uri"` では「https://doi.org/10.…」の文字全体を `<uri xlink:href>` にする。Word のハイパーリンクが付いていても、表示文字が URL そのもの（または同じ DOI）なら同じ形にする | J-STAGE の mixed-citation の子要素は uri・pub-id などで ext-link は使えず、同じ文字をリンクと DOI の両方にはできない。ガイドラインは pub-id を推奨（引用文献リンクの反映率が上がる）。2026-10 の試験登載では pub-id は画面上リンクにならなかったが、DOI としての登録を優先する（uri にした場合も、編集登載システムで DOI 欄に手入力すれば登録できる） |

## 6.1 浮動配置の図表（テキストボックス・グループ図形）

2 段組をまたぐ図などは、テキストボックスやグループ図形に図の本体（画像・表）とキャプションを入れて配置されることが多い（2026-10 の実際の論文 3 本すべて）。
docx には Word で表示したときの位置が記録されておらず、記録されているのは図形が結び付いている段落（アンカー段落）と、そこからの距離などだけである。

- 図を置く位置の規則: Word で表示したときに、図の左上の直上にある本文の文章を含む段落の直後（図の直上が別の図表なら、さらにその上の本文）。
- 読み取り（`docx_reader`）: 浮動配置の図形を `Float`（位置の基準・距離・大きさ・折り返し）として記録し、中身の段落・表・画像に `float_id` を付ける。
  段組みと行の設定（`Layout`: 1 段の幅、行送り、1 行の字数）も `w:sectPr` と `w:docGrid` から読む。
- 機械的に配置するのは、図の左上がアンカー段落の左上にあり（縦はアンカー段落の上端から 1 行未満、横はその段の左端から 1 cm 未満。`floats.at_anchor`）、
  中身が単純（キャプション 1 つと本体 1 つ）な場合だけ。このとき、図の左上の直上の本文はアンカー段落の直前の段落なので、図をアンカー段落の前に置く。
- それ以外は「位置を決められない図表」とし、AI に位置と組み合わせを指定させる（5 章の `placements`）。依頼文には、記録された位置の説明と、
  アンカー段落から行数を数えた推定（`floats.estimate_top_left`。ページ・段の区切りは考慮しない目安）を付ける。
- AI による補完を「使わない」設定で位置を決められない図表があれば、変換を中止する（`pipeline.AIRequiredError`。コマンドラインは終了コード 2、
  Colab は手順 5 で赤い枠）。AI の回答を反映した後も残った場合（AI が位置を答えなかった、検証で採用しなかった、回答が途中で切れて
  読めなかった）は、図が結び付いている段落（アンカー段落）のすぐ後ろに仮に置く（決定事項 21。`Classifier.provisional_target`）。
  アンカー段落が、続いた箇条書きの項目（同じ番号の定義）か引用の段落の途中にあるときは、その箇条書き・引用の最後の段落の後ろに
  ずらす（`Classifier.run_end`。アンカー段落のすぐ後ろに置くと箇条書き・引用が 2 つに分かれ、図表を手作業で移しても分かれたまま
  残るため。空のアンカー段落が箇条書きの項目の間にあるときも同じ。AI が指定した位置はずらさない）。箇条書きの項目かどうかは、
  組み立て（`assemble_floats`）と同じに見る（`Classifier.list_or_quote`。画像と文字が同じ段落の項目は項目として数え、画像だけ・
  別行数式だけの項目〈図・数式になる〉、見出しと推定する段落、キャプションなどのある浮動配置でないテキストボックスの段落の前で止める。間の浮動配置の図形の中身、
  文字だけのテキストボックスの段落〈囲み・図の注記として別に扱い、その位置には出力しない。6.2〉、空白だけの段落は飛ばす）。
  AI が本文の外（注・引用文献など）の段落の後ろを指定した図表は、本文の最後（最後の章の終わり。後付けの前）に仮に置く。
  同じ位置に置く図表は、キャプションの番号順（番号がなければ後ろ、同じ番号なら docx の順）。
  手作業で正しい位置に移すよう、レポートの冒頭（要対応）・3 章（図表ごとに仮に置いた位置。`ArticlePlan.float_place`: 段落「…」の後ろ、
  または本文の最後。仮に置いた位置のすぐ前の段落に文字がなければ、その前の文字のある段落で示す。3 章の場所の欄も、アンカー段落が
  空の段落なら、その前の段落の場所）・14 章のチェックリストと Colab の赤い枠に出す（コマンドラインは終了コード 1）。レポートの冒頭・
  3 章、Colab の枠とコマンドラインは、図表ごとにキャプションと、手作業で移す XML の要素（`structure.float_targets`: 図表の ID
  〈`structure.float_ids`〉と、図形の中身から本文の段落として出した段落。どちらかがあれば、ID のないキャプションのない図も数える。
  どれもなければ「図表の中身」）を示す。中身が単純なら図の本体とキャプションを組にしてから置き、そうでなければ中身をそのまま置く。
  手動モードで AI の回答を貼り戻す前の出力でも、同じ位置に仮に置く。
- **本文の外の段落に結び付いた図形**（修正計画の N7。0.25.0）: アンカー段落が本文の外（引用文献・注・付記・謝辞・後付け・英文の部分。
  英文の部分では資料が始まる前）にある図形の中身は、その領域の段落にしない（0.24.1 までは、図形の中身が引用文献・注・英文要旨などの
  段落になり、画像は XML に入らなかった）。図表の入った図形は、図の左上の位置にかかわらず「位置を決められない図表」にし（理由
  「図形が本文の外（引用文献）の段落に結び付いている」など。決定事項 10）、AI を使わない設定では止める（`pipeline.AIRequiredError`）。
  AI が本文の段落を指定すればその後ろ、指定がなければ本文の最後に仮に置く（決定事項 21 の後半。`provisional_target`。アンカー段落が
  本文の段落でないので本文の最後）。グループ図形の画像は、アンカー段落（本文の外の段落）から集めて図に入れる（中身が単純なとき
  〈画像とキャプション 1 つ〉と、AI がその画像を図の body に指定したときだけ。中身が単純でない図形〈画像・図キャプション・注記など〉を
  仮に置くとき〈手動モードで AI の回答を貼り戻す前、AI が画像を指定しなかったとき〉は、画像は図に入らず、XML に入らなかった画像
  〈要対応。4.3〉として知らせる。このとき「位置を決められなかった図表」の要対応は「XML の本文の最後にある図表の中身」を移すよう
  案内するが、図形の中身がすべて除外の段落なら、本文の最後には何も出ていない。画像だけの浮動配置のグループ図形〈図形の中に段落も
  表もないもの〉は、本文の外の図形として記録しないので、今までどおり XML に入らなかった画像〈要対応〉になる。どちらも範囲外で、
  黙っては消えない。F の点検の 1 回目で書いた）。文字だけのテキスト
  ボックスは 6.2 の囲み・注記の判定で扱い、囲みなら本文の最後に置いて要確認にする。資料（`<app>`）の中の図形は、今までどおり資料の
  中に出す。浮動配置でない（行内・VML の）テキストボックスで、キャプション・画像・表を含むものは、今までどおりその領域の段落
  （範囲外。7 章）。引用文献などの段落そのものにある画像（図形の外の画像）は、今までどおり XML に入らなかった画像として要対応で知らせる
  （4.3。修正計画の N1）。
  どの図形が本文の外かは、英文の部分では資料が始まったかどうか（`build_front_en` の中でしか分からない）で決まり、本文はその前に
  組み立てるので、構造の組み立てを 2 回行う（`structure.classify`）: 1 回目に `build_back`・`build_front_en` が、本文の外の図形の
  中身（浮動配置の図形の段落・表と、浮動配置でない文字だけのテキストボックスの段落）を、状態を変えずに飛ばして記録し
  （`Classifier.outside`。図形の ID -> 領域）、記録があれば、1 回目が段落に書き込んだもの（役割・役割の由来・覚え書き）を戻して
  組み立て直す。2 回目は `split_regions` がその中身を本文の最後に回す（docx の順。領域の状態は変えない）。本文の外の図形がない原稿は
  1 回だけ（0.24.1 と同じ処理・同じ判断の番号）。2 回目に新しく本文の外の図形が見つかることはない（見つかっても飛ばすだけで、出力にも
  除外にもならないので、不変性チェックが「出力漏れ」で不合格になり、黙っては消えない）。
- 表で組んだ図（問題文など）は `<fig>` の中に `<table-wrap>` を入れる（JATS 1.1 の fig は table-wrap を含められる。修正計画の決定事項 22。
  J-STAGE の画面での表示は要確認）。
- 図形の中の表 1 つのセルに画像と図キャプションが並ぶもの（セルごとに画像とキャプション、画像の行とキャプションの行、キャプション
  1 つで画像がいくつかのもの）は、組み方が一つに決まれば、AI を使わない設定でも、セルの画像を図の本体、セルのキャプションを図の
  キャプションにした図に組む（表としては出さない。`Classifier.cell_figures`。画像だけのセルとキャプションだけのセルが並ぶ表は、
  同じ列の上下か同じ行の左右に隣り合う組が、表全体で一つの向きに決まるときだけ。`cell_pairs`）。セルに表キャプション・キャプションで
  ない文字（「（a）」などの小見出しも）・入れ子の表があるとき、画像とキャプションの組を一つに決められないときは、組まずに、今までどおり
  （0.21.0 と同じ）キャプションのない表として出す（図の左上がアンカー段落の左上にある図形は、AI を使わない設定でも止めず、アンカー
  段落の前に置く。位置を決められない図形は、今までどおり AI に位置と組み合わせを任せる）。セルに画像がない表（図キャプションと
  問題文だけの表など）と、セルに図キャプションがない表も、今までどおり表として出す。組んだ図のキャプションと、画像と同じ段落の文字は、
  docx では表のセルの段落なので、出版版 PDF との照合（4.4）では今までどおり表のセルとして扱う（照合しない・ルート2 で直さない。
  `ArticlePlan.cell_paras`、`linker.body_paragraphs` の文脈 cell）。
- 画像のない図キャプションの直前（図キャプションを図の上に置く原稿では直後）にある、キャプションのない表は、その図の本体にする
  （fig の中の table-wrap。`Classifier.table_for_figure`。どちらの向きかは、画像の図のキャプションが画像の上と下のどちらに多いかで
  決め、画像の図がなければ下とみなす）。表とキャプションの間にほかの段落がある、表に表キャプションが付いている、表が逆の向きにある、
  直後の表の次に表キャプションがある（どちらの表か決められない）ときは組まず、要対応（「図の本体」）としてレポートの冒頭・3 章・
  14 章、Colab の赤い枠、コマンドラインに出す（要対応なので、コマンドラインの終了コードは 1。0.22.0 では、表の文字は XML に入って
  いるとして終了コードを変えなかったが、修正計画の D で要対応の扱いを 3 章の `report.actions` にそろえた）。近くにキャプションのない表が
  なければ、今までどおり判断の一覧（4 章）に記録するだけにする。理由ごとの対処（3 章。`report.figure_body_detail`）: 間に段落が
  ある・逆の向きにあるときは、表を図キャプションの隣に置き直す。表に表キャプションが付いているときは、表を動かすのではなく、図の
  本体の画像があるか、表キャプションと図キャプションのどちらが正しいかを確かめる。
- 位置を決められない図表（仮の位置に置いた図形）の中身は、本当はそこにないので、図表を組み立てるとき（`Classifier.assemble_floats`）に、
  その外の要素と組にしない（図キャプションと画像、表キャプションと表、キャプションのない表に後ろの表キャプションを付けること、
  キャプションの続き、本文スタイルの図表キャプションの推定の隣、図の本体の表〈`table_for_figure`〉）。前後の要素は、同じ置き場所の
  要素（図形の外の要素なら図形の外の要素、仮に置いた図形の中身なら、同じ位置に仮に置いた図形の中身）だけで数える
  （`structure.same_place`。置き場所は仮に置いた位置で分ける。間に図形の中身を仮に置いていても、docx で隣り合う画像と
  図キャプション、表と表キャプションは組にする。同じ段落に結び付いた、画像だけの図形とキャプションだけの図形は、同じ位置に
  仮に置くので 1 つの図に組む〈0.21.0 と同じ。Word の原稿で、画像とキャプションを別々の図形にして浮かせる形〉。別々の段落に
  結び付いた図形は、別の位置に仮に置くので組にしない。ただし、同じ箇条書き・引用の別々の項目に結び付いた図形〈どちらも箇条書き・引用の
  終わりに置く〉と、AI がどちらも本文の外の段落の後ろと答えた図形〈どちらも本文の最後に置く〉は、同じ位置に仮に置くので組にする。
  0.21.0 と同じ扱いで、キャプションが 2 つ以上あるときに画像をどのキャプションと組むかは推定にすぎない）。手作業で移す図表の知らせ（XML の要素）にも、図形の中身だけが出る。
  AI が位置を指定した図形と、位置が機械的に決まる図形の中身は、今までどおり隣の要素と組にする（キャプションだけの図形の
  キャプションと、隣の本文の画像など）。囲み（文字だけのテキストボックスの `<boxed-text>`。6.2）は、図表を組み立てるときに隣の
  要素として数えない（置き場所 `structure.BOX_PLACE`。0.24.1 までは囲みの文字を除外していて要素の列になかったので、画像と図キャプション、
  表キャプションと表、キャプションのない表と画像のない図キャプションの間に囲みを置いても、0.24.1 と同じく組にする。図はキャプションの
  位置に組み立てるので、画像とキャプションの間にあった囲みは、キャプションが画像の後ろなら図の前に、前なら図の後ろに出る。表は
  表キャプションと表の先に来る方の位置に組み立てるので、間にあった囲みは、キャプションが表の上でも下でも表の後ろに出る。F の点検の 1 回目で直した。
  0.25.0 の最初の実装では、囲みを隣の要素と数えたので、本文スタイルの「図1」の段落がキャプションにならない、画像とキャプションの間に
  囲みが 2 つあると図が 2 つに分かれる、などで図表を組めなかった）。
- 図形の中で画像と文字（説明文など）が同じ段落にあるときは、画像を図の `<graphic>` に入れ（段落の中には出さない）、段落は文字ごと
  図の直後に本文の段落として出す（機械的に組む場合も、AI がその画像や段落を図の本体に指定した場合も同じ。レポートの判断の一覧に記録する）。
  位置を決められない図形なら、手作業で移す XML の要素の知らせに、図表の ID と並べてその段落も示す（「F1・F2 と段落「説明文：…」」。
  図表だけを移すと、段落が仮の位置に残るため）。
  キャプションのない図形では図にしないので、これまでどおり画像も文字も 1 つの段落に出す。
- 図の位置の推定に、記事の PDF は使わない（PDF が docx と同じ版とは限らないため）。
- 領域（和文の冒頭・本文・後付け・英文の部分。`structure.Classifier.split_regions`）は、図形の外の段落・表だけで決める。図形の中の段落・表
  （浮動配置でない VML・行内のテキストボックスの中のものも）では、スタイルや文字にかかわらず領域を切り替えず（図形の中のセクション区切りでも
  切り替えない）、その時点の領域に入れる（テキストボックスの中の「英文要旨」スタイルの段落や「注」だけの段落で、以降の本文と引用文献が
  英文要旨や注に入らないように）。図形の中身は結び付いている段落（アンカー段落）の後ろに並ぶので、アンカー段落と同じ領域に入る。
  ただし、アンカー段落が和文の冒頭の最後の段落（セクション区切り）なら、区切りで切り替えた後の本文に入る（テンプレートの冒頭に図形はない
  ので、本文の中身とみなす。0.18.1 と同じ）。図形の中の題目の段落も、冒頭の最後のセクション区切りで本文に切り替える条件（題目を見たこと）に数える。
  本文の外の段落に結び付いた図形の中身は、2 回目の組み立てで本文の最後に回す（上の N7）。

## 6.2 文字だけのテキストボックス（囲み・図に重ねた注記）

問題文・ヒントなどの囲みは、数学教育の論文によくある。画像・表・図表キャプションを含まないテキストボックス（「文字だけの
テキストボックス」）を、囲み（本文の `<boxed-text>`）、図に重ねた注記（矢印・点・辺の名前など。本文に出さない）、決められない
もの、空白だけのものに分ける（修正計画の D1。0.25.0。0.24.1 までは、すべて図の一部とみなして除外していた）。

- 読み取り（`docx_reader`）: テキストボックス（`w:txbxContent`）ごとに `model.TextBox`（ID x1, x2, …、アンカー段落、DrawingML か VML か、
  行内〈wp:inline、または position:absolute のない VML〉か、VML の position:absolute か、グループ図形・描画キャンバスの中か、浮動配置の
  図形の ID、幅・高さ）を記録し、中の段落・表・表のセルの段落に `textbox_id` を付ける。入れ子の内側のテキストボックスの段落は、外側の
  ID を継ぐ（内側の TextBox は作らない）。幅は wp:extent（グループの中なら wps:spPr の a:ext に、一番外側のグループの拡大率〈wp:extent /
  a:chExt〉を掛ける）か VML の style の pt。pt 以外の単位（cm・in・%・グループの座標）は読めないとして None。本文（word/document.xml）の
  テキストボックスだけを記録する（脚注・文末脚注の中のものは、今までどおり注の段落）。文字の読み方は変えない。
- 対象（`Classifier.text_only`）: テキストボックスの最上位の要素に、表・画像のある段落・図表キャプション（キャプションのスタイル・
  役割、または「図N」「表N」の形）がなく、図表の入った浮動配置の図形（位置を決められない図表・機械的に置く図表）の一部でもないもの。
  対象外（今までどおり）: 図表の入った図形（グループ図形を含む）の中のテキストボックス（修正計画の F の (9)。図表の一部）、表のセルの段落に
  結び付いたもの（中身は表のセルに出る）、和文の冒頭・資料の中・脚注の中のもの。
- 判定（`floats.textbox_kind`。上から順に。文字数は空白を除いた文字の数で、数式・脚注の参照は 1 字。幅は 1 段の幅に対する割合。
  幅か 1 段の幅を読めなければ、囲みの規則では幅の条件を使わず、図の注記の規則は当てはめない〈黙って除外する注記に倒さず、決められない

## 7. 既知の限界

- Word の図形・グループ図形・グラフは画像化できない（docx に画像ファイルがない。PDF などから画像を用意する）。用意する画像のファイル名と図の題目を、レポートの冒頭（要対応）・14 章のチェックリスト・Colab の赤い枠・コマンドラインの表示に出す（`report.images_to_prepare`）。
  そのときだけ、利用者に画像を求める（ノートブックは手順 7、1 画面版は「画像を入れる」の欄、コマンドラインの `--images`）。受け取った画像（PNG・JPEG など、または 1 ページの PDF）は
  出力ファイル名の形式にして Graphics/ に入れ、ZIP とレポートを作り直す（`pipeline.add_images`。レポートの 9 章では「利用者が用意」。読めない画像があれば ValueError で、1 枚も入れない。
  コマンドラインは終了コード 2）。
  Word の図形を LibreOffice で描かせて画像を作る方法もあるが、描き方が Word と少し違い、仕上がりを人が確認する必要があるので採らない。
- アップロード用の ZIP には、記事フォルダに残っている前の変換の残り（今回指定しなかった PDF、今回は出力しなかった画像など）を入れないが、
  記事フォルダからは消さない（レポートの 10 章に出す）。Colab の手順 8 でダウンロードする「変換結果」の ZIP（出力フォルダ全体）には残る。
  ZIP の読み直し（`package.zip_problems`）は、名前の文字・記事フォルダの外と中の想定外の項目・0 バイトのファイル・XML があることだけを見る。PDF がない
  こと（EMSGM057E）は 14 章のチェックリストで知らせ、PDF の中身（別の記事の PDF でないかなど）はここでは確かめない。
- 最後のページ（`lpage`）は NFKC で正規化するだけで、文字は確かめない（ZIP 名・フォルダ名に使わないため。「12頁」のような入力も
  知らせずにそのまま XML の `lpage` に入る）。確かめるなら、止めずに知らせる形にする。
- ルビは親文字のみ。
- 引用の抽出は著者・年方式と `[1]` 形式の番号方式。上付き番号の引用方式には未対応（AI 補完で補える）。
- 段落の役割の推定は、番号の形式（「１．」「(1)」「①」）、隣接する画像・表、テキストボックス内の「図N」「表N」からの規則による。
  テンプレートにあるスタイルが別の役割の段落に付いている場合（本文に章見出しスタイルなど）は、スタイルを信じて推定しない。
- テキストボックスやグループ図形に入った図表の位置は、多くの場合 AI の判断になる（6.1）。docx から行数を数えた推定は、ページや段の区切りを考慮しない。
  AI でも決まらなかった図表の仮の位置（アンカー段落の後ろ）は近い位置にすぎず、2 段組では別の段・別のページの図が多いので、手で移す
  作業は残る。仮に置いた図形の中身はその外の要素と組にしないので（6.1。同じ位置に仮に置いた図形の中身どうしは組にする）、
  本文の画像に重ねたキャプションだけの図形を仮に置くと、本文の画像とは組にならない（キャプションだけの図と、キャプションのない
  図になる。AI が位置を指定すれば、今までどおり隣の画像と組にする）。AI の指定で、画像の段落と図キャプションの間や、箇条書き・
  引用の途中の段落の後ろに図表を置いたときは、今までどおり画像とキャプションが組にならない・箇条書き・引用が 2 つに分かれる
  （指定どおりに置く）。仮の位置を箇条書きの終わりにずらすとき、途中の図形の中の段落（キャプションなどのある浮動配置でない
  テキストボックスの段落など。文字だけのテキストボックスの段落は飛ばす）の前で止めるので、その後ろに同じ箇条書きの項目が続くと、
  箇条書きが 2 つに分かれる。同じ箇条書き・引用の別々の項目に結び付いた図形と、
  AI がどちらも本文の外の段落の後ろと答えた図形は、同じ位置に仮に置くので組にする（6.1）。仮に置いた図形の中身に引用スタイルや自動番号の
  段落（画像のある段落）があると、隣の本文の `disp-quote`・`list` とまとめられる（箇条書き・引用のまとめは置き場所を見ない。知らせには
