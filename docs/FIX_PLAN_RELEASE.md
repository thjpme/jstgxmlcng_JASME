# 修正計画（正式リリースの前。2026-11 の実地テストとソース点検に基づく）

`docs/FIELD_TEST_2026-11.md`（実地テストとソース点検の結果。問題の番号 C001〜C163、優先度、詳細、決定事項）の問題を、どの順に、
どの担当（モデル）で直すかの計画。**この計画はまだ実装していない**（コードは 0.31.1 のまま）。
問題と同じく、ルート1（docx から作る。両方のルートに関わるものを含む）とルート2（出版版 PDF で補う）に分ける。

## 方針

1. **まず「黙って誤る」をなくす。** 修正必須の 26 件（ルート1 が 18、ルート2 が 8）は、正しく変換できるようにするか、
   できない形を見つけて要対応で知らせる（ルート2 は、誤った直しを作らず、直さずに理由を付けて 13 章に出す）。
   「正しく変換する」直しが大きいものは、**先に知らせ（守り）だけを入れ、正しい変換は次の版に回す**（詳細の「直し方（リリース前の最低限）」と
   「直し方（その後）」）。守りは、builder や照合の判断に頼らない別の実装で足す（`lost_images`・`table_problems`・`lost_autonums` と同じ並び）。
2. **原則はそのまま守る。** docx の文字を変えない（読み落としていた文字を読むのは、文字を変えることではない）。出力しない段落は理由付きで記録する。
   知らせは `report.actions()` に `Action` を足すだけ。ルート2 で docx を直すのは `pdfdocx.py` だけで、決められない違いは直さない側に倒す。
   原則との兼ね合いで判断が要るもの（白字の文字、私用領域の記号、囲い文字、字間の空白を入れた氏名など）は、決定事項として所有者が決めてから直す。
3. **出力の形を変える直しは、版の 2 桁目を上げてまとめる。** 守りと知らせだけの直しは出力の形を変えないが、要対応が増える
   （今まで終了コード 0 だった原稿が 1 になる）ので、これも 2 桁目を上げる。
4. **実際の原稿を回帰の基準にする。** 直す前に、28 論文・46 docx の両ルートの出力（XML・要対応と要確認の key・レポートの 13 章の件数）を
   基準として保存し、単位ごとに差分を出して、変わった所が直しの狙いどおりかを確かめる（`tests/private/` の中だけ。コミットしない）。
   テストに足す docx は、実際の原稿から**形だけ**を写した架空の内容を `tests/make_fixtures.py` で作る（原稿そのものは入れない）。

## 担当の割り振り

直しは Sonnet か Haiku を原則とし、難しい所だけ Opus、最後の手段として Fable を使う。全体の監督は Fable が行う。

| 役 | 担当 | すること |
|---|---|---|
| 監督 | Fable | 単位の設計の確認（直す前）、決定事項の反映、単位をまたぐ食い違いの調整、点検の指摘の採否、版ごとの最終確認。コードは原則として書かない |
| 実装（普通） | Sonnet | 修正必須・高の大半。1 つの単位の中で、問題ごとに「再現のテスト → 直し → 全テスト」 |
| 実装（機械的） | Haiku | 文言、文書の食い違い、定数・設定、決まった形のテストの追加、ノートブックの作り直し |
| 実装（難しい） | Opus | 照合（`pdfmatch`）の分類・窓の決め方、図・表の本体の組み立て（`structure.py` の `place_floats` まわり）、氏名の分け方など、既存の判断を組み替える直し |
| 点検 | Sonnet（回帰・利用者向け）、Opus（原則） | 単位ごとに、原則・回帰・利用者向けの 3 つの観点で点検する。修正と再点検は最大 3 回。収束しなければ反映せず、所有者に相談する（CLAUDE.md） |

## 1 つの単位の進め方

1. 監督（Fable）が、単位の問題の詳細と決定事項を読み、設計（どの関数をどう変えるか、足す `Action` の key と文、足すテスト）を短く書く
   （`docs/fix_plan_release/units/` に置く。`docs/fix_plan_2026-11/units/` と同じ形）。
2. 実装の担当が、問題ごとに、再現のテスト（今は失敗する）→ 直し → `python -m pytest -q` を行う。fixture は `tests/make_fixtures.py` に足す。
3. 実際の原稿 46 docx を両ルートで変換し直し、基準との差分を出す。狙いと違う差分があれば直す。
4. 点検（原則・回帰・利用者向け）。指摘の採否は監督が決める。修正と再点検は最大 3 回。
5. 文書（`docs/DEVELOPMENT.md`・`ARCHITECTURE.md`・`DESIGN.md`・`USAGE.md`、`docs/FIELD_TEST_2026-11.md` の末尾の「対応の記録」）を合わせる。
6. Python 3.10 でも通ること（`tests/test_syntax.py`。CI の 3.10 を直した後は CI で）。

## 見積もりの前提と、確かめていないこと

- 担当と規模は検証者の見立てで、実装してみると変わりうる。特に B（図・表）と P（照合）は、1 つの直しがほかの原稿の結果を変えやすい。
- 「中」以下は検証していない。直す単位に入ったときに、まず再現を確かめる。
- 実地テストの docx は元原稿を機械的にテンプレートへ流し込んだもので、著者が書いた原稿とはスタイルの付き方が違う可能性がある。
  0.32.0 の後に、著者が書いた形の原稿でも数件試すのがよい。
