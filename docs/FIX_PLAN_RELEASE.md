## 所有者の決定（2026-11-12）

### 前提の変更

1. **著者に、校正後の docx も提出してもらう**（学会の作業の流れ。ツールの外）。docx と出版版 PDF の違いは、原理的には形式的なもの
   （記号・全角半角など）だけになる。ただし人のミスはありうる（著者の直し忘れ、古い版の提出、印刷所が組版で直した箇所、別の論文のファイル）。
2. **ルート2 は、校正の直し (B) を docx に書き込まない**（選択式でも残さない）。直すのは組版の違い (A) だけで、それでも食い違う箇所は
   要確認で知らせる。(A) は今までどおり docx に変更履歴つきで書き込む。(A) に、誌の句読点の統一（「．」→「。」、「、」→「，」）を足す。
   上付きの数字、字形だけの違い（「⑴」と「（1）」）、箇条書きの記号、注番号の形、英文題目の末尾の「:」は、直さず、知らせない（13 章に件数だけ）。
3. **図・表の画像は、作業する人がすべて用意する。** ツールは docx の中の画像を書き出さない（EMF/WMF の変換、Word のトリミングの
   切り取りもやめる）。ツールの役割は、(1) どの図にどの名前の画像が要るかを示す、(2) 入れた画像を受け取って ZIP に入れる、
   (3) 足りない画像を知らせる、(4) 入れた画像と図の対応を、docx を直して変換し直しても・AI の回答を反映しても崩さない、
   (5) 図番号・キャプション・入れた画像を並べた、取り違えの確かめの一覧を出す、の 5 つ。キャプションのない画像（本文の中、表のセルの中）も
   同じ扱い。数式の画像は対象にしない（テンプレートでなくなる見込み）。
4. **AI による補完は必須にしない。ただし、図の位置を合わせるための、強く推奨する仕上げとする。** AI を使わずに変換したときは、
   位置を決められない図を結び付いた段落の後ろに置き、AI を使うと位置が合うことを知らせる。**AI には出版版 PDF を渡すことを強く推奨する**
   （API で自動実行するときは、依頼文と一緒に PDF を渡す。手動モードでは、依頼文と画面で PDF の添付を勧める）。依頼文は、PDF が
   添付されていなくても答えられるように作る（AI に「PDF を見て答えたか」を答えさせ、見ていなければ記録する）。
5. **警告は最小限にする。** 毎回必ずやる手順（画像を入れる、AI の回答を入れる）は、要対応・要確認とは別の「手順」の区分にする。

### 設計の見直し（2026-11-12。前提の変更を受けて、3 つの視点で調べた結果。所有者が採用）

| 見直す点 | 決めたこと |
|---|---|
| 違いの分類 | 「直すか」でなく「知らせるか」で引き直す。(1) 表記の違いで直す・知らせない（今の (A) と句読点の統一）、(2) 表記の違いで直さない・知らせない（上付き・字形・箇条書きの記号・注番号の形など）、(3) 内容の違いで直さない・1 つの要確認にまとめる、(4) 照合できなかった所は 13 章の記録だけ |
| PDF の知らせ | `pdf_diff`・`pdf_unfixed`・`pdf_ignored` の 3 つをやめ、内容の違いだけを並べる要確認 1 つにする。重さは要確認。PDF にだけある行（著者が docx に戻し忘れた一節）は拾わない |
| ルート | 1 本にする（PDF を付ければ (A) を直す。直さない動作はコマンドラインの指定に残す） |
| 別の論文のファイル | 題目が PDF に見つからず、段落の半分以上が見つからないときは、変換を中止する |
| 書誌情報 | 巻・号・ページ・受付日・採用日を PDF から読んで入力欄に先に入れる。入力を書き換えて PDF と違えば知らせる |
| 題目・著者・所属 | PDF の 1 ページ目にあるかの確かめを 1 つ作り、著者・題目のスタイルの誤りをまとめて要対応にする |
| 画像の持ち越し | 画像の名前を図番号から決め、同じ記事なら変換し直しても入れた画像を持ち越す |
| レポート | 組版の違いの全件の表は件数だけにする。「変更履歴を確認する」の手順をなくす。することの一覧を冒頭に置く |
| 和文の題目の中の改行 | 今の出力のまま、要確認から記録に下げる（テンプレートの注意書きで防ぐ） |
| 表のセルの中の文字 | 今は PDF と照合しない（docx の文字の中央値 5%、多い論文で 30%）。簡易な確かめ（セルの文字が PDF のどこかにあるか）を足す。見つからないセルは、PDF との食い違いの知らせ（W3）の中に載せる（知らせの種類は増やさない。誤報の割合を実際の原稿で測ってから条件を決める） |

## 方針

1. **まず「黙って誤る」をなくす。** 修正必須の（決定を反映した後の） 9 件（ルート1 が 7、ルート2 が 2）は、正しく変換できるようにするか、
   できない形を見つけて知らせる。守りは、builder や照合の判断に頼らない別の実装で足す（`lost_images`・`table_problems`・`lost_autonums` と同じ並び）。
2. **原則はそのまま守る。** docx の文字を変えない（読み落としていた文字を読むのは、文字を変えることではない）。出力しない段落は理由付きで記録する。
   知らせは `report.actions()` に `Action` を足すだけ。docx を直すのは `pdfdocx.py` だけで、直すのは組版の違い (A) に限る。
   所有者の決定で原則の文が変わる所（ルート2 が (B) を書き込まない、画像を書き出さない、ルートが 1 本になる、「手順」の区分）は、
   実装のときに CLAUDE.md と `docs/DEVELOPMENT.md` の「守るべき原則」を書き直す。
3. **警告を増やさない。** 知らせを足すときは、取れる行動が 1 文で書けること、実際の原稿で対応が要った割合を測ってあることを条件にする。
   PDF と照らせば分かるものは、PDF との食い違いの知らせ（W3）か、題目・著者・所属の確かめ（W6）にまとめ、個別の知らせを増やさない。
4. **出力の形を変える直しは、版の 2 桁目を上げてまとめる。**
5. **実際の原稿を回帰の基準にする。** 28 論文・46 docx の両ルートの出力を基準として保存してあり、単位ごとに差分を出して、変わった所が
   直しの狙いどおりかを確かめる（`tests/private/` と作業用フォルダの中だけ。コミットしない）。テストに足す docx は、実際の原稿から
   **形だけ**を写した架空の内容にする。校正後の docx の実物はまだないので、次の号の 1〜2 論文で、警告の件数を測る。

## 担当の割り振り

直しは Sonnet か Haiku を原則とし、難しい所だけ Opus、最後の手段として Fable を使う。全体の監督は Fable が行う。

|---|---|---|
| 監督 | Fable | 単位の設計の確認（直す前）、決定事項の反映、単位をまたぐ食い違いの調整、点検の指摘の採否、版ごとの最終確認。コードは原則として書かない |
| 実装（普通） | Sonnet | 修正必須・高の大半。問題ごとに「再現のテスト → 直し → 全テスト」 |
| 実装（機械的） | Haiku | 文言、文書の食い違い、定数・設定、決まった形のテストの追加、ノートブックの作り直し |
| 実装（難しい） | Opus | 照合（`pdfmatch`）の分類、図・表の組み立て（`structure.py`）、氏名の分け方など、既存の判断を組み替える直し |

## 1 つの単位の進め方

1. 監督（Fable）が、単位の問題の詳細と決定事項を読み、設計（どの関数をどう変えるか、足す `Action` の key と文、足すテスト）を短く書く
   （規模 L の W1・W2・W8 は `docs/fix_plan_release/units/` に設計書を置く）。
2. 実装の担当が、問題ごとに、再現のテスト（今は失敗する）→ 直し → `python -m pytest -q` を行う。
3. 実際の原稿 46 docx を両ルートで変換し直し、基準との差分を出す。狙いと違う差分があれば直す。
4. 点検（原則・回帰・利用者向け）。指摘の採否は監督が決める。修正と再点検は最大 3 回。
5. 文書（`docs/DEVELOPMENT.md`・`ARCHITECTURE.md`・`DESIGN.md`・`USAGE.md`、`docs/FIELD_TEST_2026-11.md` の末尾の「対応の記録」）を合わせる。
6. Python 3.10 でも通ること（`tests/test_syntax.py`）。

## 見積もりの前提と、確かめていないこと

- 担当と規模は検証者の見立てで、実装してみると変わりうる。特に W1・W2・W8 は設計から要る。
- 「中」以下は検証していない。直す単位に入ったときに、まず再現を確かめる。
- 校正後の docx の実物はまだない。「校正後の docx なら警告は 1 論文 0〜3 件」は、ツールが補った docx を代わりに使った見積もり。
- 各社の API の PDF の入力は、公式の文書で確かめただけで、実際には呼んでいない（2026-11-12 時点。Claude・ChatGPT・Gemini は対応、
  Sakana AI は一部のモデルだけで 4 MB まで）。日本語・2 段組みでの精度は、どの社の文書にも書かれていない。
- 実地テストの docx は元原稿を機械的にテンプレートへ流し込んだもので、著者が書いた原稿とはスタイルの付き方が違う可能性がある。
