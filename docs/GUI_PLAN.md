# 操作画面（GUI）の整理計画

- 作成: 2026-11-01
- 対象: main の 0.25.0（コミット c35defd）。この計画の時点では、コードは変えていない。
- 目的: Colab の画面が「ごちゃごちゃしている」問題を、**後任に引き継ぎやすく・保守しやすい**という条件を外さずに解く。
- 依頼された 2 つの問い
  1. Colab とは別に、もっと分かりやすい簡単な GUI を上から重ねられるか
  2. 1 とは独立に、Colab 上の文字を減らし（仕様書には残してよい）、必要な情報に集中させられるか

## 0. 現状の整理（何がごちゃごちゃなのか）

ノートブック（0.25.0）の文字の量を数えた（`notebooks/JASME_docx_to_JSTAGE_XML.ipynb`）。

| 場所 | 文字数 | 内容 |
|---|---|---|
| 冒頭の説明（テキストセル） | 約 1,500 字 | 手順の一覧表、作り方 2 通りの説明、注意 5 項目 |
| 各手順の入力欄の説明（`#@markdown`） | 約 3,900 字 | 入力欄 25 個の上の説明。変数名（`volume` など）を併記 |
| 「API キーについての詳細」（テキストセル、開閉式） | 約 4,200 字 | キーの作り方・料金・モデル・他社 API |
| 手順 6 の説明（テキストセル） | 約 500 字 | 回答の貼り付け方 |
| 合計 | **約 1 万字** | 本文の説明だけで。変換後にはさらに 14 章のレポート全文が画面に出る |

利用者（編集担当者。プログラムは書かない）から見た問題を、原因ごとに分ける。

| 問題 | 原因 | 計画での扱い |
|---|---|---|
| 読む量が多い | 説明書の内容（作り方の違い、API キーの作り方、料金）がノートブックに入っている | 説明書に移し、画面は 1 行の案内と「詳しくはこちら」にする（3 章） |
| 入力欄が多く、どれが必須か分からない | 25 個の入力欄が同じ見た目で並ぶ。通常は触らない欄（`CONVERT_EMF`・`USE_DEV_VERSION`・`MODEL`・`OTHER_MODEL`・`SPLIT_LABELS`・DOI・その他の原稿種別）も同列 | 必須／任意／詳細設定に分け、詳細設定は畳む（3 章・4 章） |
| 「手順 ○ を先に実行」「前の論文の値が残っている」などの注意が多い | Colab ではどのセルも押せてしまうので、順序の確認（`DONE`・`guard`）と書き換え忘れの確認が必要 | 順序の確認はセルの構造から来る問題。ボタンの有効・無効で制御する画面（4 章）なら消える |
| 変換後の画面が長い | 赤い枠（要対応・要確認）の後にレポート全文（14 章）を出している | 要対応と要約だけを出し、全文は開閉式にする（2 章の共通部分） |
| 要対応と要確認が同じ赤い枠 | `colab.result_boxes()` が `Action.level` で色を分けていない | 色を分ける（2 章の共通部分） |
| 変数名（`volume`、`AI_MODE`）が画面に出る | Colab のフォームは変数名を欄の名前として表示する | 日本語の欄名にする（3 章。方法は要確認）か、フォームをやめる（4 章） |

いま守られている設計は変えない: **変換の本体はパッケージ（`src/jasme_jats/`）にあり、ノートブックは薄い操作画面にすぎない**（`docs/DESIGN.md` の 2 章）。
`report.actions()` が知らせの唯一の出所であること（`docs/DEVELOPMENT.md` の原則 8）も変えない。この 2 つがあるので、操作画面を取り替えても変換の結果は変わらず、テストも流用できる。

## 1. 案の比較

「Colab とは別の GUI を重ねる」案（問い 1）と「Colab の文字を減らす」案（問い 2）を、ほかの案も含めて並べる。
評価の軸は、利用者の分かりやすさのほかに、**引き継ぎ・保守**（依存するもの、コードの置き場所、ブラウザなしでテストできるか、後任が直すのに要る知識）。

| 案 | 内容 | 利用者から見て | 引き継ぎ・保守 | 判定 |
|---|---|---|---|---|
| **A. Colab の中に 1 画面のアプリ（ipywidgets）** | ノートブックは「準備」「画面を開く」の 2 セルだけ。画面はパッケージの `app.py`（新設）が ipywidgets で組む。ファイルのドラッグ＆ドロップ、入力欄、「変換」ボタン、進捗、結果、ダウンロードが 1 画面に並ぶ。手動モードの貼り付け欄や足りない画像の欄は、必要なときだけ現れる | 手順の番号・▶ の順序・「先に手順 ○ を」が消える。Colab の仕組み（セル）を意識しなくてよい | ipywidgets は Colab に最初から入っていて、長く安定している。画面の論理は Python だけ（JavaScript 不要）。画面の状態（何が押せるか）をパッケージの中のクラスにすれば pytest で確かめられる。Colab と無関係なので Jupyter でも動く | **採用の第一候補**。ただし Colab での動作（ファイルのアップロードの上限など）を試作で確かめる（5 章の S1） |
| B. Colab の中に Gradio の画面 | A と同じ構成で、画面を Gradio で組む。Colab の出力欄に埋め込んで表示できる | A よりさらに Web アプリらしい見た目 | 依存が 1 つ増え、Gradio は版の変化が速い（1 年で表示の API が変わることがある）。Colab での埋め込み表示が壊れた例もある。後任が Gradio を知っている必要がある | A が動かなかったときの代替。A を選ぶ理由は「依存を増やさない」 |
| C. Colab の外の Web アプリ（Streamlit Cloud・Hugging Face Spaces・Cloud Run など） | 常時公開のサーバーに置く | いちばん簡単（リンクを開くだけ） | **不採用の理由は `docs/DESIGN.md` の 2 章のまま**: サーバーの維持・費用・管理者が要る。未公開原稿を外部のサーバーに上げる。LibreOffice・AI の API キーの置き場所も要る | 不採用 |
| D. パソコン用の配布ファイル | PyInstaller などで実行ファイルにする | インストールが要る | OS ごとの作成・更新。LibreOffice を同梱できない（DESIGN 2 章） | 不採用 |
| **E. 今のノートブックのまま文字を減らす（問い 2）** | 説明を説明書に移す、欄を必須／任意／詳細に分ける、変換後は要約だけ出す、セルを 9 → 6 に減らす | 見た目は今と同じ「セルを順に押す」形。読む量は 1/3 以下にできる | 変更は `tools/make_notebook.py` と `colab.py` だけ。小さく、すぐ反映できる。ただし「順序の確認」「前の論文の値が残る」の仕組みは残る | **A の前に行う部分（共通部分）と、A が成功すれば捨てる部分に分けて行う**（2 章） |

### 判定の要点

- 問い 1 の答え: **できる**。A（Colab の中の 1 画面アプリ）が、条件（引き継ぎ・保守）を満たす唯一の「重ねる」案。
  Colab を捨てるのではなく、Colab は「実行環境」としてだけ使い、**利用者が見るのは 1 画面のアプリ**にする。
  サーバーを持たない・原稿が利用者の環境から出ない・コードが `main` から毎回入る、という今の利点はそのまま。
- 問い 2 の答え: **できる**。しかも、E のうち「説明書に移す」「要約だけ出す」「枠の色を分ける」は A でもそのまま使う共通部分なので、先に行って損はない。
  E のうち「セルの並べ替え・統合」は、A が成功すれば不要になる。
- A と E は独立ではなく、**E の共通部分 → A の試作 → （試作の結果で）A か E の残りか**、の順に進めるのがむだがない。

## 3. 文字を減らす（問い 2）の具体策

### 3.1 説明書に移す（G1）

ノートブックに書いてある説明のうち、**その場で読まなくてよいもの**を説明書に移し、ノートブックには 1 行と参照だけ残す。

| 今の場所 | 移す先 | ノートブックに残すもの |
|---|---|---|
| 冒頭の手順の一覧表・作り方 2 通りの説明・注意 5 項目（約 1,500 字） | README の「使い方」（すでに同じ内容がある。重複を消して README を正とする） | 「論文の docx を J-STAGE の XML にします。上から順に ▶ を押してください。説明書: リンク」の 2〜3 行と版の表示 |
| 「API キーについての詳細」（約 4,200 字） | 新しい説明書 `docs/USAGE_AI.md`（仮。API キーの作り方・登録・料金・モデル・他社 API） | 手順 4 の欄の 1 行「API キーの登録のしかた: リンク」 |
| 手順 2 の作り方 2 通りの長い説明（約 740 字） | README の「出版版 PDF との照合と、2 通りの作り方」（すでにある） | 選択肢の名前と「PDF がまだないときは『docx から作る』」の 1 行 |
| 手順 6 の貼り付け方（約 500 字） | `docs/USAGE_AI.md` の「手動モード」 | 「回答（json のコードブロック）を下に貼り付けて ▶」の 1 行。うまくいかないときの対処は、エラーの文（`report.actions`）に書いてあるので画面には不要 |
| 手順 7・8・9 の説明（約 1,000 字） | README の「使い方」 | 各 1 行 |

README は今 51 KB あり、利用者向けと開発者向けが混ざっている。G1 で **利用者向けの部分を `docs/USAGE.md`（仮）に切り出し、README は概要と各文書へのリンクにする**ことを提案する
（必須ではない。切り出さなくても G1 はできる。切り出すなら HANDOFF.md の「読む順番」も直す）。

### 3.2 変換後の表示を「要約が先、全文は畳む」にする（G1）

今は手順 5・6 で、赤い枠の後にレポート全文（Markdown、14 章）を出している。これを次の順にする。

1. 要対応の枠（赤）・要確認の枠（**黄**。今は両方赤。`colab.result_boxes()` で `Action.level` によって色を分ける）
2. 結果の要約（不変性チェック・DTD・アップロード時チェック・PDF との照合。今も print している 5 行）
3. 「レポート全文を見る」（HTML の `<details>` で畳む。中身は今と同じ Markdown の表示）

`colab.py` に `summary_box(res)` と `report_details(markdown)` を足すだけで、ノートブック側は数行減る。手順 8 のダウンロード後の表示も同じ部品を使う。
これは 4 章の 1 画面アプリでもそのまま使う。

### 3.3 知らせの文を短くする（G1。任意）

赤い枠の文（`Action.box_title` / `box_detail`）は `report.py` にあり、レポートの 14 章と同じ出所なので、ノートブックを直すのではなく `report.py` で見直す。
長い枠（PDF の照合の枠など）は、**1 行目に「何をすればよいか」、2 行目以降に詳細**の形にそろえる。文の内容は変えず、順序だけ直す。
`tests/test_colab.py` と `tests/test_report.py`（相当）の期待値を合わせて直す。

### 3.4 入力欄を必須・任意・詳細設定に分ける（E'。A が通らなかったときだけ）

| 区分 | 欄 | 見せ方 |
|---|---|---|
| 必須 | 作り方、docx、PDF、巻、号、最初のページ、最後のページ、査読の有無、原稿種別、AI による補完の方法 | 手順 2・3 に残す。説明は欄の名前だけ |
| 任意 | 最終査読日、キーワード（日・英）、発行日、J-STAGE 公開日、受付日、受理日、責任著者 | 手順 3 の後半に「任意」の見出しで |
| 詳細設定 | CONVERT_EMF、USE_DEV_VERSION、MODEL、OTHER_MODEL、SPLIT_LABELS、DOI、その他の原稿種別（日・英） | ノートブックの最後の「詳細設定（通常は変えない）」の見出しの下に 1 セルにまとめ、見出しを畳んだ状態で保存する。手順 1・4・5 は、その変数がなければ既定値を使う |

### 3.5 セルを 9 → 6 にする（E'）

| 今 | 後 |
|---|---|
| 1 準備 | 1 準備（詳細設定を外に出す） |
| 2 作り方と アップロード、3 書誌情報、4 AI の方法 | 2 設定と書誌情報（作り方・AI の方法・書誌）、3 アップロードして変換（アップロードは `files.upload()` が対話的なので変換と同じセルに置ける。手順 2 の「作り方」はアップロードの前に決まっていればよい） |
| 5 変換 | （3 に統合） |
| 6 回答の貼り付け | 4（手動モードのときだけ） |
| 7 足りない画像 | 5（必要なときだけ） |
| 8 ダウンロード、9 次の論文 | 6 ダウンロード（ダウンロードが済んだら自動で次の論文の準備をし、「次は手順 2 から」と出す。手順 9 は消える） |

`guard`/`mark` の仕組みは残す（番号が変わるだけ）。`tests/test_notebook.py` の手順番号を直す。

### 3.6 欄の名前を日本語にする（E'。要確認）

Colab のフォームは変数名を欄の名前に使うので、`volume = ""  #@param` の代わりに `巻 = ""  #@param` と書けば「巻（volume）」の併記が要らなくなる
（Python 3 は日本語の識別子を許す）。Colab の `#@param` の解析が日本語の識別子を受け付けるかは未確認なので、G2 の試作で確かめる（5 章の S5）。
受け付けないなら、変数名はそのままにし、説明を「巻」だけにして `（volume）` の併記をやめる（エラーの文も日本語の欄名で書く）。

## 4. 1 画面アプリ（問い 1。単位 G3）の設計

### 4.1 画面

1 列に上から並べる。番号も ▶ もない。押せないものは灰色にする。

```
┌ 論文 docx → J-STAGE XML 変換  版 0.27.0            説明書 ─┐
│ 作り方   (●) 出版版 PDF に合わせてから作る  ( ) docx から作る │
│ docx     [ファイルを選ぶ]  論文.docx                        │
│ PDF      [ファイルを選ぶ]  論文.pdf                         │
│ 書誌情報  巻[  ] 号[  ] ページ[  ]〜[  ]  査読 (●)あり ( )なし │
│          原稿種別 [研究論文 ▼]                              │
│          ▸ 任意の項目（キーワード・日付・責任著者）           │
│ AI       ( ) 使わない (●) 手動  ( ) API（Claude）  ▸ 詳細設定 │
│                                   [ 変換する ]              │
│ ── 進捗 ──────────────────────────────────────────────── │
│ LibreOffice を準備中… / 変換中… / AI に依頼中…              │
│ ── 結果 ──────────────────────────────────────────────── │
│ [赤] 要対応 …    [黄] 要確認 …                              │
│ 不変性チェック 合格 / DTD 合格 / アップロード時チェック 問題なし │
│ （手動のとき）依頼文 [コピー]  回答を貼る [          ] [反映]  │
│ （必要なとき）足りない画像  図1 [ファイルを選ぶ]              │
│ [ 結果をダウンロード ]   ▸ レポート全文      [ 次の論文 ]      │
└─────────────────────────────────────────────────────────┘
```

- 「変換する」は docx（とルート2 なら PDF）と必須の書誌情報がそろうまで押せない。足りない欄は欄の横に赤く出す。
- 「結果をダウンロード」は要対応が残っていれば一度確認（今の手順 8 と同じ。「このままダウンロード」のボタンで進める）。
- 「次の論文」は、ファイルと論文ごとの欄（ページ・キーワード・日付・DOI）を空にする。巻・号・査読・AI の設定は残す（同じ号を続けて変換するため）。
  今の「前の論文の値が残っている」の警告は不要になる（`colab.carried_over()` / `same_first_page()` は消すか、`AppState` に移す）。
- 手動モードの回答の貼り付け欄・足りない画像の欄は、必要になったときだけ現れる（今の手順 6・7 の「〜のときだけ」の説明が要らない）。
- 詳細設定（EMF 変換・開発版のブランチ・モデル名・図表番号を分ける・DOI・その他の原稿種別）は畳んでおく。

### 4.2 コードの置き場所

| ファイル | 役割 |
|---|---|
| `src/jasme_jats/app.py`（新設） | 画面。2 層に分ける。**`AppState`**: 入力の値と進み具合を持ち、「変換を押せるか」「次に何を見せるか」を決める。ipywidgets に依存しない純粋な Python。**`build_app(state, io)`**: ipywidgets を組み立て、ボタンを `AppState` と `pipeline.convert()` につなぐ |

| `io`（`build_app` に渡す小さなオブジェクト） | Colab に依存する 3 つの操作だけを持つ: ファイルのダウンロード（`google.colab.files.download`）、シークレットの読み出し（`google.colab.userdata`）、LibreOffice のインストール。テストでは偽物を渡す。Jupyter では HTML のダウンロードリンクと環境変数で代用 |
| `tools/make_notebook.py` | 新しいノートブックも同じスクリプトで生成する（`cells_simple` を足す）。セルは 2 つ: 「1. 準備」（今の手順 1 と同じ。pip と LibreOffice）、「2. 画面を開く」（`from jasme_jats.app import launch; launch()`）。「ランタイム → すべてのセルを実行」でも動く |
| `pyproject.toml` | `[project.optional-dependencies]` に `colab = ["ipywidgets>=7.7"]` を足し、`dev` にも入れる。Colab には入っているので、手順 1 の pip では `[ai,images]` のまま |

### 4.3 テスト
